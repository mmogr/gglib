Facts about `mmogr/modelpipe-ffi` found while building its 0.6 stack (PRs #17, #18 and the pairing PR) on 2026-09-15.

- **A worktree must end in a directory named `modelpipe-ffi`** (`~/.local/src/worktrees/modelpipe-ffi/<slug>/modelpipe-ffi`): `scripts/swift-smoke.sh` synthesises a package that depends on the crate by path, and SwiftPM takes a path package's identity from its directory name, so a worktree called `drop-and-watch` fails with "unknown package 'modelpipe-ffi'". Same reason ggchat's worktrees are `<slug>/ggchat`.
- **The Makefile hardcodes `target/debug/libmodelpipe_ffi.dylib`** (`make swift`), so `CARGO_TARGET_DIR` breaks it. Symlink the worktree's `target` at a directory under `/private/tmp` instead.
- **`binding-check` fails on an uncommitted regenerated binding by design** (`git diff --exit-code -- Sources/Modelpipe/`). Commit, then gate at the hash. `make swift` copies only `modelpipe_ffi.swift`, so a hand-written extra file in `Sources/Modelpipe/` survives.
- **`make surface` is a static name check**; the Swift smoke test itself runs only in CI's `apple` job. Run `make xcframework-fast && ./scripts/swift-smoke.sh` locally for any PR that changes an exported member (about a minute warm). Its stdout is lost on a crash.
- **A `uniffi::Record` is a plain Swift struct**: `print` renders every field, so a redacting Rust `Debug` redacts nothing in Swift. Redact with a hand-written `CustomStringConvertible` extension beside the generated file. Never call a method on a `MpPipe(noHandle:)` placeholder; it segfaults.
- **PRs open one at a time against `main`**: CI runs only for PRs based on `main`, `ci-success` is the single required check, and the repo squash-merges, so one PR per conventional commit is what gives release-plz's CHANGELOG its lines. Subjects must be sentences; release-plz publishes them verbatim.
- **The next release is 0.2.0**: `release-plz.toml` has `features_always_increment_minor = true`. 0.1.4 was bumped but never built or tagged (no `v0.1.4` or `build/v0.1.4`; `Package.swift` pins 0.1.3). Merging the release PR pushes `build/vX.Y.Z`; `release.yml` builds, pins the checksum and tags `vX.Y.Z` itself.
  - **Superseded 2026-09-21: released 0.3.0; the next is 0.4.0.**
- **Every release manufactures the next release PR, and an open one must be left alone** (found 2026-09-21, at 0.3.0 with PR #28 open). `release.yml:247` commits `chore(release): pin the v<version> XCFramework checksum` to main, and release-plz counts that commit as releasable — so an *empty* release PR whose only changelog line is that pin appears after every release. #28 is one. **Merging** it burns a version on nothing: a ~23-minute `macos-26` build, a new zip, another pin commit, and PR #29 — non-terminating. **Closing** it hits the trap already recorded in modelpipe's own `release-plz.toml` ("the moment that PR is closed or merged, the next run opens a new one… closing it produced #20, not a draft"), and a non-draft release PR invites a reflex merge that pushes a build tag. Do neither: release-plz force-updates the same branch, so landing real `feat:` commits retitles the open PR in place.
- **The build-tag → release-tag path has a measured 2-in-7 failure rate and is not re-runnable.** Build tags exist for v0.1.0–v0.1.4, v0.2.0, v0.3.0; release tags are missing for **v0.1.1 and v0.1.4**. `release.yml:69-94` refuses a version whose release exists, and where the pin commit landed but the release did not, a re-run computes a *different* checksum — the build is not byte-reproducible. Single points of failure that all fire *after* the long build: `secrets.RELEASE_PAT` pushing to main (`:213,:252`), `make binding-check` green at the tag (`:125`), and the 10-minute resolve gate (`:299-307`). Budget for a patch release after any 0.x.0.
- uniffi 0.32.1's Swift generator is byte-identical to 0.32.0's: neither calls `rust_future_cancel`, so cancellation is an explicit object (`MpWatch` with a `CancellationToken`).
- **release-plz's `release` job has never tagged in this repo, because `Cargo.toml` said `publish = false`** (found 2026-09-15, fixed by #22). `release-plz release` considers only packages whose manifest `publish` is absent or a non-empty list (`is_publishable()` in `next_ver.rs`), logs `nothing to release` otherwise, and never reaches its git-only tagging path; the release-PR side walks every workspace package, so release PRs opened while the tag never followed (#7, #9, #15, #20 all logged it; every `build/v*` tag was hand-pushed). The fix is `publish = ["nowhere"]`, a registry allow-list naming no configured registry: `cargo publish` still stops before uploading, release-plz sees the package and takes the git-only branch under `release-plz.toml`'s `publish = false`. Verified with the real binary: `release-plz release --dry-run` in a clone of the release-PR merge commit (a branch must be checked out, `--git-token $(gh auth token)`) prints `nothing to release` as merged and `skipping the following: ["creation of tag 'build/vX.Y.Z'"]` with the fix. A release-PR merge that already happened cannot be re-tagged by it (the merge commit carries the old manifest and later pushes are not release-PR merges), so 0.2.0 got one hand-pushed `build/v0.2.0` at `b80bf1d` (done 2026-09-15; `v0.2.0` published at `1866b2f`).
- **`release.yml`'s last step ("A consumer can actually resolve it") can time out downloading the 210 MB asset on the runner while the release is fine** (v0.1.3 and v0.2.0; #24). Check from a Mac: download the asset, `swift package compute-checksum` against `Package.swift` at the tag, `swift package resolve` and a `.dynamic` consumer `swift build`.
- **The tag ledger must contain the manifest's version before release-plz moves on.** 0.1.4 was bumped and never tagged, so every run said "local version (0.1.4) > registry version (0.1.3). Only changelog will be updated" and opened no PR; the owner had `build/v0.1.4` pushed at `a823634` with `release.yml` disabled (a record like `build/v0.1.1`: prepared, never built), after which release-plz proposed 0.2.0. Never build a phantom version for real: `release.yml` would tag it on a main whose generated Swift is ahead of the artifact, and ggchat's `from:` floor would resolve to it.

**Why:** each cost a failed run or a review round before it was known.

**How to apply:** lay out ffi worktrees and targets as above before the first build; budget a local xcframework-fast plus smoke run per PR; open the ffi PRs sequentially. Related: [[gglib-remote-arc-conclusion-run]], [[gglib-stacked-pr-and-arm-testability]].
