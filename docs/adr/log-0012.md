# ADR 0012 log

A dated log for [ADR 0012](0012-the-remote-tunnel.md) while the remote arc is open. Entries are appended, never edited. When the arc closes they are folded into the ADR as one dated note, rather than as further amendments to it during the arc.

## 2026-09-15: pairing moves to the tunnel edge

gglib now pairs through modelpipe 0.6. `ServeHandle::invite` mints the device's key and name and holds the key at the edge; gglib stores both, then arms the code; the edge answers `POST /modelpipe/pair` itself. The proxy no longer sees a pairing request, and `modelpipe::pair` on the joining side connects, waits for the far machine and only then presents the code.

**The correction history `docs/remote.md` carried, moved here.** Its paragraph "Pairing moves a one-time code, not the key" carried a block headed "Corrected 2026-09-07, and again 2026-09-12". What it recorded:

- On 2026-09-07 no one path had all three of the two-minute window, the burn at the third wrong code, and the ticket being needed. Over the tunnel a wrong code was a wrong bearer, refused at the edge before gglib saw it, so gglib's own counter never saw those guesses.
- Once the ticket started lasting, the edge counted wrong bearers itself (`grant_once_bounded`, three attempts), so over the tunnel the burn and the window both held, and the arithmetic stopped resting on a ticket that no longer changed.
- On the desktop's own loopback the burn counted, but `POST /v1/remote/pair` needed no ticket, so a local process could end a pairing that was on screen with three POSTs (gglib #1045).

With the code answered only at the edge, that hole is closed: the proxy's loopback pairing route is gone, so three POSTs no longer end a pairing. Wrong codes are counted per endpoint at the edge, three each, and anything holding the ticket, a local process included, can still end an invite by guessing from sixty-five endpoints, which this machine logs as burned. The paragraph in `docs/remote.md` now says what is true and points here, instead of adding a third correction beneath the other two.

## 2026-09-15: what the move supersedes in ADR 0012, and the decisions taken with it

ADR 0012 is not amended during the arc. These are the principal sentences in it that edge-served pairing makes untrue, kept here to be folded in when the arc closes. Line numbers are at gglib `6b349957`, before the move.

**Superseded**

- `:552-560` and `:683-684`, the 2026-09-12 amendments saying every key in `data/remote_devices` is put back on the listener whatever identity it binds with. These were already inaccurate before the move: since #1034's fix, `arm` seeds only the keys the roster lists (`crates/gglib-app-services/src/remote/serve_arm.rs:84-91` reads the roster's ids and `:145` passes them to `device_keys::seed`), so a key with no row is not put back.
- `:363` ("desktop calls `ServeHandle::grant_once(code, 120s)`"), `:367-371` (the `POST /v1/remote/pair` walkthrough), and the dated notes about `grant_once_bounded` and the burn arithmetic at `:396-397`, `:406-412`, `:421-428` and `:515-518`. The code is an invite now, answered by the edge at `POST /modelpipe/pair`, with three wrong codes per endpoint and the invite ended as burned when a sixty-fifth endpoint guesses.
- `:281-292`, point 4 of decision 2's 2026-09-11 amendment, "`POST /v1/remote/pair` refuses a device that already holds a key". The edge refuses a pairing request from a device whose key it holds, before it looks at the code.
- `:302-303`, point 5 of the same amendment, "Settings keeps ids, labels, when the invite was minted, when a device redeemed it, and when it was last seen". It keeps the endpoint that redeemed the invite too.
- `:685-686`, "under `TokenPolicy::Named` the listener admits only a device's key or a live code". The listener admits no code as a key now; the edge answers a code only on its own pairing route.
- `:885`, "`/v1/remote/pair` sits outside the bearer group but inside `remote_marker`". The route is gone.
- `:1072`, "says so in `first_contact.rs`". The first-contact wait is `ConnectHandle::wait_reachable`, and `connect_open.rs` carries the budgets.
- `:1286`, under *Out of scope*, "Per-peer pinning of the pairing request". modelpipe 0.6 has the mechanism: an invite reports the endpoint that redeemed it, and a token can be pinned to one. gglib records the endpoint and pins nothing, as the plan decided.
- `:1127`, the sample log line `POST /v1/remote/pair 200 → dev-bd905f7d`, is a dated reading and stays as it is; the route it names is gone.

**Decided with the move**

- **Device ids are modelpipe's.** `ServeHandle::invite` mints `dev-` and eight hex digits, and gglib-core's `generate_device_id` and `generate_pairing_code` are gone. modelpipe's code draw is uniform over all million values by rejection sampling, where gglib's took a 122-bit random draw modulo a million.
- **Nothing cancels the task that waits for an invite to end.** Whoever takes an invite out of the gateway, the waiting task, a new offer or a session reset, records how it ended, and the reset does so before the roster's writer goes. So a device that redeemed just before `disable`, and that nothing had recorded yet, is still listed.
- **A `join` with a code runs to completion once modelpipe's `pair` has it.** `disconnect` answers at once and the pairing finishes, in at most 25 seconds of waiting plus modelpipe's 30-second exchange, because abandoning it could spend the code on a pairing nobody collects. A `join` without a code is still ended at once.
- **A coded `join` waits 25 seconds for the far machine**, so the pairing ends within 55 seconds, inside the 60 the CLI gives the command. A `join` without a code waits 30.
- **The connecting side keeps no lasting identity.** `ConnectOptions::identity` stays unset, so a device presents a new endpoint each time it connects; the endpoint recorded at redemption says only which endpoint redeemed the code.
- **The drain window is modelpipe's, and it no longer covers a pairing.** Its listener withdraws a live invite when it closes, which is where the drain starts, so a pairing request whose code the edge has not redeemed by then is refused with the edge's one refusal, and the joining device reports a refused code. Before the move the proxy redeemed a code during the drain. The window is one pairing exchange, which `modelpipe::pair` sends in a single write, so it is rarely met.
- **gglib #1045 is closed.** The proxy's loopback pairing route is gone, so three POSTs no longer end a pairing. Anything holding the ticket, a local process included, can still end an invite by guessing from sixty-five endpoints, which this machine logs as burned.
- **Compatibility.** A laptop on gglib 0.18 or a phone on ggchat 0.2.4 cannot pair with this version, and a laptop on this version cannot pair with a desktop on gglib 0.18, whose edge spends the code on the attempt. Devices already paired keep working.
