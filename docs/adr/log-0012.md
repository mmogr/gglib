## 2026-09-15: pairing moves to the tunnel edge

gglib now pairs through modelpipe 0.6. `ServeHandle::invite` mints the device's key and name and holds the key at the edge; gglib stores both, then arms the code; the edge answers `POST /modelpipe/pair` itself. The proxy no longer sees a pairing request, and `modelpipe::pair` on the joining side connects, waits for the far machine and only then presents the code.

**The correction history `docs/remote.md` carried, moved here.** Its paragraph "Pairing moves a one-time code, not the key" carried a block headed "Corrected 2026-09-07, and again 2026-09-12". What it recorded:

- On 2026-09-07 no one path had all three of the two-minute window, the burn at the third wrong code, and the ticket being needed. Over the tunnel a wrong code was a wrong bearer, refused at the edge before gglib saw it, so gglib's own counter never saw those guesses.
- Once the ticket started lasting, the edge counted wrong bearers itself (`grant_once_bounded`, three attempts), so over the tunnel the burn and the window both held, and the arithmetic stopped resting on a ticket that no longer changed.
- On the desktop's own loopback the burn counted, but `POST /v1/remote/pair` needed no ticket, so a local process could end a pairing that was on screen with three POSTs (gglib #1045).

With the code answered only at the edge, that hole is closed: the proxy's loopback pairing route is gone, so three POSTs no longer end a pairing. Wrong codes are counted per endpoint at the edge, three each, and anything holding the ticket, a local process included, can still end an invite by guessing from sixty-five endpoints, which this machine logs as burned. The paragraph in `docs/remote.md` now says what is true and points here, instead of adding a third correction beneath the other two.

## 2026-09-15: what the move supersedes in ADR 0012, and the decisions taken with it

ADR 0012 is not amended during the arc. These are the principal sentences in it that edge-served pairing makes untrue, kept here to be folded in when the arc closes. Line numbers are at gglib `6b349957`, before the move.

**Superseded**

- `:552-560` and `:683-684`, the 2026-09-12 amendments saying every key in `data/remote_devices` is put back on the listener whatever identity it binds with. These were already inaccurate before the move: since #1034's fix, `arm` seeds only the keys the roster lists (`crates/gglib-app-services/src/remote/serve_arm.rs:84-91` reads the roster's ids and `:145` passes them to `device_keys::seed`), so a key with no row is not put back.
- `:363` ("desktop calls `ServeHandle::grant_once(code, 120s)`"), `:367-371` (the `POST /v1/remote/pair` walkthrough), and the dated notes about `grant_once_bounded` and the burn arithmetic at `:396-397`, `:406-412`, `:421-428` and `:515-518`. The code is an invite now, answered by the edge at `POST /modelpipe/pair`, with three wrong codes per endpoint and the invite ended as burned when a sixty-fifth endpoint guesses.
- `:281-292`, point 4 of decision 2's 2026-09-11 amendment, "`POST /v1/remote/pair` refuses a device that already holds a key". The edge refuses a pairing request from a device whose key it holds, before it looks at the code.
- `:302-303`, point 5 of the same amendment, "Settings keeps ids, labels, when the invite was minted, when a device redeemed it, and when it was last seen". It keeps the endpoint that redeemed the invite too.
- `:685-686`, "under `TokenPolicy::Named` the listener admits only a device's key or a live code". The listener admits no code as a key now; the edge answers a code only on its own pairing route.
- `:885`, "`/v1/remote/pair` sits outside the bearer group but inside `remote_marker`". The route is gone.
- `:1072`, "says so in `first_contact.rs`". The first-contact wait is `ConnectHandle::wait_reachable`, and `connect_open.rs` carries the budgets.
- `:1286`, under *Out of scope*, "Per-peer pinning of the pairing request". modelpipe 0.6 has the mechanism: an invite reports the endpoint that redeemed it, and a token can be pinned to one. gglib records the endpoint and pins nothing, as the plan decided.
- `:1127`, the sample log line `POST /v1/remote/pair 200 → dev-bd905f7d`, is a dated reading and stays as it is; the route it names is gone.

**Decided with the move**

- **Device ids are modelpipe's.** `ServeHandle::invite` mints `dev-` and eight hex digits, and gglib-core's `generate_device_id` and `generate_pairing_code` are gone. modelpipe's code draw is uniform over all million values by rejection sampling, where gglib's took a 122-bit random draw modulo a million.
- **Nothing cancels the task that waits for an invite to end.** Whoever takes an invite out of the gateway, the waiting task, a new offer or a session reset, records how it ended, and the reset does so before the roster's writer goes. So a device that redeemed just before `disable`, and that nothing had recorded yet, is still listed.
- **A `join` with a code runs to completion once modelpipe's `pair` has it.** `disconnect` answers at once and the pairing finishes, in at most 25 seconds of waiting plus modelpipe's 30-second exchange, because abandoning it could spend the code on a pairing nobody collects. A `join` without a code is still ended at once.
- **A coded `join` waits 25 seconds for the far machine**, so the pairing ends within 55 seconds, inside the 60 the CLI gives the command. A `join` without a code waits 30.
- **The connecting side keeps no lasting identity.** `ConnectOptions::identity` stays unset, so a device presents a new endpoint each time it connects; the endpoint recorded at redemption says only which endpoint redeemed the code.
- **The drain window is modelpipe's, and it no longer covers a pairing.** Its listener withdraws a live invite when it closes, which is where the drain starts, so a pairing request whose code the edge has not redeemed by then is refused with the edge's one refusal, and the joining device reports a refused code. Before the move the proxy redeemed a code during the drain. The window is one pairing exchange, which `modelpipe::pair` sends in a single write, so it is rarely met.
- **gglib #1045 is closed.** The proxy's loopback pairing route is gone, so three POSTs no longer end a pairing. Anything holding the ticket, a local process included, can still end an invite by guessing from sixty-five endpoints, which this machine logs as burned.
- **Compatibility.** A laptop on gglib 0.18 or a phone on ggchat 0.2.4 cannot pair with this version, and a laptop on this version cannot pair with a desktop on gglib 0.18, whose edge spends the code on the attempt. Devices already paired keep working.

## 2026-09-20: the fifth reading's two "cancelled" pairings have a probable cause, and it is not the issue that was named

The fifth reading recorded two pairings that "paired and connected but carried nothing past the pairing POST": in each, the phone's one further request — a model list — never reached the edge, the phone said "Could not reach the server: cancelled", and a third pairing after the app was reinstalled worked from its first request. The reading left them unexplained and said the phone's log for that window was not collected. It still has not been, and the window has long since rolled out of the phone's buffer.

A 2026-09-14 review guessed ggchat #69 — a background during a QR scan cancelling the pipe. It does not fit. First, #69's races both need a `.background`, and `RootView` at that version starts tasks for `.active` and `.background` and ignores `.inactive`; a scan sheet is presented inside the app and a Control Centre pull does not background it, so neither of the evening's events supplies one. Second, and on its own decisive, neither race can end in a cancelled URLSession task: race 1 leaves a session whose tunnel is gone, which this device's own end of the pipe answers `502 tunnel_unavailable` — a different sentence — and race 2 leaves the composer's task not running at all, so there is no request and no alert. Third, it is not needed: #69's fix (ggchat #97) shipped in v0.3.0, after which #126 reproduced the same sentence on v0.3.2.

**The candidate that fits is ggchat #126's first cause**, fixed in #127 and shipped in v0.3.3: on iOS 27.0, with the split view collapsed as it is on a phone, a conversation opened from the list after going back from one is told it has disappeared within a millisecond of appearing, SwiftUI calls its tasks off as they start, and the model list asked for there fails as "Could not reach the server: cancelled". At 0.2.2 that is the only code path that can print that string for a model list: `.transport` is the one `ProviderError` case carrying the "Could not reach the server:" prefix, `perform` is its only producer on the list path, and nothing in the app cancels that request itself — there is no per-pipe `URLSession` and no `invalidateAndCancel` anywhere in `Sources` at that tag. `Composer.swift` is the same blob from v0.2.0 through v0.3.2, so the phone that evening and the phone in #126 ran the same code.

**The competing explanation, and why the sentence rules it out.** This reading places both failing connections among those that changed path — `b94f776587f0` at 19:29:39 and `fc3bcb92a8ab` at 21:01:42 — and says the 21:01 list was made about six seconds after wifi was switched off and the connection had moved to the relay. A request lost to a moving network is the obvious candidate, and the alert's own wording is what rules it out: `.transport` carries the `URLError`'s `localizedDescription` verbatim (`OpenAICompatibleProvider.swift:69`), so a request that left the phone and lost its network reports what the network did — the connection lost, the Internet offline, a timeout — and never `cancelled`. A cancelled task reports `cancelled`, which is what the phone showed.

**Measured, 2026-09-20.** ggchat at tag v0.2.2, on an iOS 27.0 iPhone simulator (`iPhone 17e`, UDID `99BC652A-58C3-4ADF-8F06-03BAFACFD9EA`), with a provider pointing at a closed loopback port so that the walk discriminates rather than demonstrates: a request that is attempted fails at the socket and names a connection failure, and a request that is never attempted says `cancelled`. Twice, with no assertion failing:

| conversation | alert at v0.2.2 (two runs) | alert at v0.3.3 (one run) |
|---|---|---|
| first of the launch | "Could not reach the server: Could not connect to the server." | the same |
| opened from the list, after going back from one | **"Could not reach the server: cancelled"** | "Could not reach the server: Could not connect to the server." |

The first conversation is the control within a run, and #127 measured it as unaffected for the same reason: its task is not called off, so its request reaches the socket. The pill reads the same on both rows — the port is dead either way — and is there to confirm no list landed, not to tell the rows apart.

**The walk at v0.3.3**, on the same simulator, gives a connection failure in *both* rows, in one run: the second conversation's request is attempted and refused, because #127's fix hands the work to a task the model owns rather than to the view's. That is the control that matters, because nothing in the reading's path changes but the app. The walk differs in one step — at v0.3.3 the back button is taken by the navigation bar's leading index rather than by its identifier, which is what the repo's own walks do — and that step is upstream of the alert: both versions hold at `tap(back, untilExists: "New conversation")` until the list is actually on screen, so both reached the second conversation by the same test before any alert was read.

Three runs are discarded, none for its reading. Two failed at the back tap, which never reached the list, so what looks like their second reading is the first conversation's alert read twice. The third failed earlier still, at the wait for a back button, so no tap was made at all — and it is the one to know about, because it recorded a single `cancelled` from a state the walk never established. A reader grepping these logs finds three `cancelled` lines where only two are readings. No server, no daemon and no key were involved in any of this.

**What this does not establish.** That the openings at 19:29 and 21:01 met that trigger — that the owner had already been inside a conversation in that launch, and opened the second from the list. The ADR does not record the navigation and the phone's log for that window is gone, so this cannot be recovered. What the evening does offer is the reinstall: a reinstall wipes the persisted conversations, so the first conversation after it is also the first of its launch, which is the case #127 measured as unaffected — and that pairing "worked from its first request". The `Composer` guard then keeps it working, because a list that has landed is never asked for again. That is consistent with the mechanism rather than discriminating between candidates: a fresh install works under #69 too.

The two failures are therefore **probably** this, and the bullet in the fifth reading stays as it is rather than being rewritten as explained. The `tunnelled_requests` count cannot help either way: both failures pre-date the counted daemon run, which began at 21:07:54, and a request cancelled on the phone, one refused by the phone's own connecting side and one refused at the edge all leave that counter untouched.

## 2026-09-21: the backend's permission, and an empty endpoint key that could brick `enable`

gglib now builds its serve-side backend as a `modelpipe::BackendUrl` rather
than as its own `Backend` struct, and pins modelpipe `0.7.0-rc.1` in both
manifests that name it. Two things in that are worth a dated note rather than
just a diff.

**The permission travels with the address now.** `ServeOptions::allow_private_backend`
is gone upstream; `BackendUrl::at` derives from the bind address both the
rewrite gglib used to do — a wildcard becomes the loopback literal of its own
family, keeping the port — and the permission a LAN bind needs. gglib's
mirrored copy of modelpipe's locality rule, written to *predict* a verdict it
could not ask for, is deleted along with the five tests — seven
`allow_private` assertions, across fifteen addresses — that pinned the
prediction. No behaviour changes for any address: the same binds are admitted
and the same ones refused.

The hazard the change introduces is quiet, so it is written down here as well
as in the code. Handing `serve` a URL *string* still compiles and converts
through `BackendUrl::dial`, which permits no private address — so a careless
migration would leave every LAN-bound proxy failing to arm, with no build
error to say why. What guards it is structural: with `Backend` and its `url`
field deleted there is no string to pass by accident.

**An empty `remote_identity` is now discarded before `serve` reads it.**
modelpipe 0.7 refuses an empty identity file rather than minting over it, and
the refusal is permanent and deliberate — a file that exists may be a key
devices are already paired against. 0.7 can no longer produce an empty one,
but every modelpipe gglib has shipped against wrote that file in place, where
a crash between the open and the bytes leaves exactly this state; and nothing
in gglib has ever deleted the file. Without the heal, a desktop that crashed
once mid-write could never `remote enable` again, and the remedy would reach
its operator only inside a failure they have no reason to go looking for.

**Empty is the only state healed.** A file with unreadable bytes in it may
still be the key this machine is paired under, so deleting it would unpair
every device to make one enable succeed. That one keeps modelpipe's refusal,
which is the operator's to act on.

## 2026-09-21: a desktop too old to pair is recognised by its status, not by modelpipe's words

`connect_open.rs` matched the literal sentence modelpipe 0.6 carried in
`PairError::Unexpected` — "a status other than 200 or 401" — and a comment
above the arm admitted as much. modelpipe 0.7 moved every status other than
200, 401 and 502 onto `PairError::UnexpectedStatus { status }`, so that arm
had been dead since the pin landed in the commit before this one: a 404 fell
to the catch-all and a desktop that was merely out of date was reported as a
fault in gglib, HTTP 500 rather than 503.

The arm is now keyed on `{ status: 404 }`, which is what a gglib 0.18 desktop
answers: its edge spends the code and its proxy has no route for the pairing
request. It keeps `GuiError::Unavailable`, so the status class is right again,
and it keeps the remedy — update the desktop, then take a new invite.

**A second arm exists so the first cannot over-reach.** Any other status is
unexplained — 404 is the only one anyone has traced to a mechanism — and an
unexplained status must not be blamed on a version, because sending an
operator after a desktop that may already be current wastes their time. Under
the old string match every status modelpipe folded into that one sentence took
the version blame with it; having the status as a number is what makes them
separable at all.

No example of a non-404 status is offered, deliberately. modelpipe's own
comment reaches for "a 503 from a proxy in front of a current serve side",
and that cannot happen here: the serve edge answers `PAIR_PATH` itself,
before the credential check and without forwarding
(`modelpipe/src/exchange.rs`, `pair_route.rs`), which is why
`gglib-proxy/src/router.rs` says pairing has no route in the proxy at all.
The arm is still required — `UnexpectedStatus` carries any status — but its
justification is the absence of a traced mechanism, not a worked example.

**Why there is no integration test for the 404.** The in-process fixture
cannot produce one — both ends are real modelpipe endpoints and the serve edge
owns the pair route — so constructing the variant *is* the evidence. That is
sound here in a way it was not before: `UnexpectedStatus { status: 404 }` is a
typed value modelpipe's own `pair_wire_tests.rs` pins, where the old string
was something gglib could construct and modelpipe could stop producing —
which is exactly what happened.

`PairError::Unexpected` survives and is still reached: modelpipe produces
"an empty key or device" among others, and the test for that case was left
where it was rather than moved with the 404.

## 2026-09-21: the idle clock comes from modelpipe, and the second nudge goes

`connect_watch.rs` kept its own idle clock — an `Instant` started on the first
`Idle` — and its own socket nudge on a minute's timer. modelpipe 0.7 carries
both: `ConnectHandle::idle_for()` and `ConnectOptions::idle_network_nudge`,
the latter on by default.

**gglib has been running two nudges, not one, since it pinned 0.7.**
`connect_open.rs` builds `ConnectOptions::default()` and never touches
`idle_network_nudge`, so the crate-side nudge has been live on every dial
since that pin landed, alongside gglib's own. This is a de-duplication rather
than an adoption; nothing is added to the options, and the cadence roughly
halves rather than staying the same.

**The clock is now read afresh on every turn rather than kept.** That is not
only tidier. `status_changed` coalesces, so a peer reached and lost again
between two of this side's polls arrives as no status at all: gglib's own
clock never saw the round trip, kept the original anchor, and called the
machine away on an idleness the pipe had abandoned. Reading `idle_for()` each
time — including after the grace elapses, rather than trusting the sleep —
puts the announcement on the idleness that is actually running.

**Two orderings are now load-bearing and both are pinned by tests.**
`idle_for()` answers `None` for a closed pipe exactly as it does for a reached
one, so `Closed` must be answered before anything reads the clock; a version
that checked presence first announced the far machine *back* as its pipe
closed. And the remaining grace is computed with `saturating_sub`, because
`Duration`'s `Sub` panics on underflow and the grace can already be spent by
the time the arm is reached.

**`away_for_s` keeps its own atomic, for two reasons rather than one.** It is
stored when Away is *announced*, about thirty seconds after the idleness
`idle_for()` measures from — that difference is constant and could in
principle be subtracted. The two that could not: it has a third state,
`None` while idle inside the grace, which is the whole point of the grace and
which an elapsed duration cannot express; and the two are different classes
of clock. `away_since` is an `AtomicI64` of unix milliseconds taken from
`SystemTime`; `idle_for()` is a `Duration` off a `tokio::time::Instant`,
which does not advance while the machine is asleep. A laptop that slept eight
hours beside an away desktop reports eight hours today and would report only
its waking seconds. No document promises that across a *local* suspend —
`docs/remote.md`'s away paragraph is about the desktop sleeping — but it is
the number a person reads, and shrinking it silently is not a refactor.

The watcher's tests split: `connect_idle_tests.rs` takes *the grace* — where
it is measured from, how long it is, and when it re-arms — because
`connect_watch_tests.rs` was 255 lines against a 300-line budget and the new
cases together would have carried it over, and because the two files are
different questions about one loop.

Two pieces of prose were already wrong before this change and are corrected
with it. `remote/README.md` described a ninety-second teardown that releases
the port; the grace is thirty seconds and nothing is torn down — that policy
was removed long ago and its paragraph outlived it. `docs/remote.md` said the
socket is nudged "every minute"; modelpipe polls the nudge once per re-dial
round, so a minute is a floor on the interval and not a period.

## 2026-09-26: `join` is the only name for dialling another machine

`gglib remote join` answered to `connect`, its earlier name, as a hidden
command that printed a note about the rename. That is gone, and so are
`POST /api/remote/connect` and the `remote_connected` event. They are
`POST /api/remote/join` and `remote_joined` now, and under them
`RemoteOps::join`, `JoinRequest`, `Joined`, `RemoteJoinBody` and
`RemoteJoinResponse`, and in the GUI `joinRemote` and `JoinSection`. The
break is clean by decision: no alias answers to the old names.

**A client and a daemon from either side of the change do not meet.**

- A client built before it posts to `/api/remote/connect`, and a daemon
  built after it answers `405`: the shipped router's `get()` fallback
  answering a `POST` to a path nothing routes.
  `crates/gglib-axum/tests/remote_join_route.rs` pins that answer.
- A CLI built after it posts to `/api/remote/join`, which a daemon built
  before it does not route. That daemon's router has the same fallback, so
  the answer is `405` there too; this is read from the router as it stood
  before the change, not run against an old build.
- `gglib remote join` probes `/health` before it posts, and when the
  daemon's build fingerprint differs from its own, `warn_on_build_mismatch`
  prints the note that names the fix, `gglib daemon stop` and a re-run,
  ahead of the failure.

**Typed now, `gglib remote connect` is refused as an unrecognised
subcommand, and clap's tip names `disconnect`, the nearest spelling, rather
than `join`.** Measured with a debug build of this change. Nothing here
overrides the tip; `docs/remote.md` says the old name is gone.

## 2026-09-26: the readings in ADR 0012's body, moved here verbatim from `a6d5eca6`

### First reading, 2026-09-06

The first evaluation of these three criteria, and it has one scope note that
outweighs every number under it: **the tunnel has never carried traffic
between two machines.** No two-machine test has been run and none exists in
the suite — `modelpipe::serve` and `modelpipe::connect` are called only from
`gglib-app-services` (`remote/mod.rs` and `remote/connect.rs`), and every test
that exercises a tunnelled request synthesizes the markers `via: 1.1
modelpipe` and `x-modelpipe-peer` against a proxy bound in-process.

So the lines below record **not yet run**, not zero.
[ADR 0010](0010-the-loop-guard-reads-what-came-back.md)'s first reading drew
this distinction for a criterion nobody had exercised — "a zero here is the
absence of the test, not its result" — and the same applies to all three here,
more strongly: writing 0 would make a feature nobody has finished testing look
like a feature nobody wants.

> this note was written, and the session is recorded under *Second reading*
> below. It supersedes the third line only: `tunnelled_requests` now has a

- **If `tunnelled_requests` stays at zero** — **not yet run.** Every daemon
  that has run this code reports `tunnelled_requests` 0 and `last_tunnelled_ms`
  `None`, and every one of them was a daemon no second machine ever dialled.
  This is the criterion a zero most easily misleads, and here it does not even
  reach the ambiguity: "nobody uses the tunnel" and "nobody has yet paired two
  machines" produce the same 0, and only the first would license deleting
  anything. Not actionable until a two-machine session exists to count.
  **OPEN.**

**All three remain OPEN, and none has been read against traffic.** What this
note establishes is the state the feature shipped in — reasoned through,
guarded, and never once run end to end — so that the first person to pair two
machines knows there is somewhere to put the number.

### Second reading, 2026-09-06 — the first two-machine session

The first time `modelpipe::serve` and `modelpipe::connect` have been on
opposite sides of a network. Everything above was written against a feature
that had never carried a byte between two machines; this note retires that
sentence and changes nothing else in the reading it amends.

**Scope.** One evening, one session, one paired peer. A macOS host served —
`Matts-MacBook-Pro`, ticket `de371f8d0f7f` — and a Linux machine connected,
peer `387480a0854e`, which is also the first time the two sides have run on
different operating systems. Every subcommand was exercised: `enable`,
`connect`, `status`, `q --remote`, `disconnect`, `kill`, and a second pairing
on a fresh ticket.

**It cannot be re-run.** `tunnelled_requests` and `last_tunnelled_ms` count
from daemon start, as the criterion itself says, and both daemons have since
stopped. Nothing stored the numbers, so this note is their only durable
record — the same provenance gap
[ADR 0009](0009-fit-the-context-to-the-machine.md)'s first reading names for
the ledger's counters, named here rather than dressed up.

**The answer came from the other machine, and that is shown rather than
assumed.** `gglib model list` on the connecting machine printed `No models
found` — an empty catalog with nothing local to serve — and `gglib q --remote`
answered anyway. The prompts carried words nothing could have had ready,
`bananaramarama` and `kumquat`, and the replies used them, which rules out a
canned answer as well as a local one.

**The counter read 0, then 1, then 4, and the 1 is the part worth writing
down.** `gglib remote status` on the serving machine reported `Requests:  0
through the tunnel` before the connect, `1` immediately after `connect`
returned and **before any prompt had been sent**, and `4` after the inference
requests. That first increment is the pairing POST itself: `POST
/v1/remote/pair` sits outside the bearer group but inside `remote_marker`,
which runs on every route, so the request that fetches the key counts like any
other tunnelled one. What shows inference crossed is the increment past 1, not
the number being non-zero. Recorded because the next person to read this
counter will otherwise be one ahead of the prompts they remember sending.

> **Amended 2026-09-07 — the quoted line has since changed wording, and the
> quote above is right.** [#986](https://github.com/mmogr/gglib/pull/986)
> landed later the same evening and made it read
> `Requests:  N served through the tunnel`, printed only on the serving
> machine; the third kill criterion above was rewritten with it, which is why
> the two strings differ in one document. `Requests:  0 through the tunnel` is
> what the build this session ran actually printed, and it is left exactly as
> it was read.

**Both transport paths were exercised, so the relay is a path traffic has
taken rather than one the design merely provides for.** On the home network
both sides reported `Path:      direct`: the hole punch held and no relay was

## 2026-09-26: the tunnel counter is the gateway's, and it still counts the pairing request

The count ADR 0012's third kill criterion reads, `tunnelled_requests`, is held
by `RemoteGateway` in `crates/gglib-app-services/src/remote/gateway.rs`. The
proxy that receives a tunnel-marked request ticks it through
`RemoteGatewayPort::note_tunnelled_request`, from `remote_marker` in
`crates/gglib-proxy/src/remote/marker.rs`. The criterion said the counter
"ticks in the proxy", which says where it is ticked from and not where it
lives; it was already `RemoteGateway`'s when #986 wrote that. The criterion
now names it where it lives.

Since #1087 the tunnel edge answers the pairing request itself, so the proxy
never sees one. #1087 chose to keep counting it: when the gateway records a
redeemed invite (`close_invite`, in
`crates/gglib-app-services/src/remote/gateway_session.rs`), it ticks the same
counter and names the endpoint that redeemed the invite as the last peer,
before it marks the session paired. #1087's commit message gives the reason:
"A redemption is counted in status as the request it was, from the endpoint
that made it, as it was while the proxy answered pairing, so the pairing
screen can name the device that paired." The gateway ticks it only for an
invite that was redeemed, so a pairing request the edge refuses is not
counted.

Decision 4's reversal, the amendment dated 2026-09-10, said that "a fortnight
