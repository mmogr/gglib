## 2026-10-24: `tools=none` keeps the opened servers' tools out of a device chat with its tools off

The phone app is getting a switch that turns one chat's tools off. A chat
the phone keeps itself goes to the Mac as
`PUT /v1/runs/{id}?kind=chat&tools=builtin`, and decision 3 offers that run
every tool of the servers `--allow-mcp` names, so the switch needs a way to
say none of them for that chat's runs. With its tools off and no Draw the
phone sends a plain chat run, which calls no tool, and nothing in gglib
changes for that. With Draw it still needs the agent loop, for the image
tool.

The change `feat(proxy): tools=none puts a device's chat run with no MCP
tool` adds that word: `?kind=chat&tools=none`, with `&draw=true` and
`&image_model=<id>` as beside `tools=builtin`. The proxy hands the starter
`no_tools` (`AgentRunStarter::start_chat`), the daemon carries it in
`chat_turn::Drawing` to `Asked::of_phone`, and `device_tools::resolve` then
returns the floor alone, listing and starting no server, as it already did
for a Mac chat whose settings turn its tools off. Draw still adds the image
tool, as decision 3's floor and ADR 0018 decision 10 have it. Without Draw
the run is an agent-loop run with no tool, which the phone does not send
and gglib accepts.

It is a new value of `tools`, not a new key, because the query is read
without `deny_unknown_fields`: a gglib from before this change reads a key
it does not know, such as `&mcp=off`, as absent and would offer the opened
servers' tools anyway. `tools` is an enum, so a word it does not know is
refused `400 invalid_request` (`?tools=mcp` is pinned so in
`crates/gglib-proxy/tests/integration_turns.rs`), and an older gglib
refuses `tools=none` rather than running the tools the person turned off.
The Context's "offering tools needs no new query word" and decision 4's "a
phone sends it nothing new" were written of `tools=builtin` alone; this
adds one word to the query and changes neither decision.

## 2026-10-25: decision 1's list is superseded by a flag on each server

[ADR 0025](0025-a-server-is-opened-to-paired-devices-by-a-flag-on-it.md)
moves the grant from the list `--allow-mcp` named onto each server's own
row, `mcp_servers.allow_remote`, set at any time by `gglib mcp allow-remote`
and `deny-remote`, by `PUT /api/mcp/servers/{id}/remote` and by the GUI.
The tunnel's gateway now says only whether a session is live, and
`--allow-mcp` is refused with a pointer to the new command. The upgrade
flags the servers a machine's list named when its tunnel was on, so a
grant in use survives it. Decisions 2, 3 and 4 stand: `/mcp` is still
refused to the tunnel, a device's run is still offered the open servers'
tools by `{id}:{tool}`, and the drawing answer still names them.
