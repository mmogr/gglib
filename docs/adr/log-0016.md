## 2026-10-09: a run that asks the person ends on the question, and the answer is the chat's next turn

The proposed decisions of the asking run, drawn before the arc opened. Line
numbers are at `0fb0b5db`. Three designs were drawn against the code and
judged through three lenses (the owner's rules, the other device in the same
day, the shipped clients and the contract); the one below held nothing while
nobody answers and won on every lens, and the two it beat are under
*Alternatives considered*.

### Context

A run is one reply the daemon owns from start to end
(`crates/gglib-app-services/src/runs/README.md:3-5`). Since
[ADR 0013](0013-the-target-is-a-value.md)'s amendments of 2026-09-29 and
2026-09-30 a run survives the client that asked for it, a paired phone reads it
live and carries a hub chat on from where the Mac left it, and Stop cancels
it. The built-in tools a daemon run is offered are read-only: without a
sandbox root the builtin adapter lists one tool, `builtin:get_current_time`
(`crates/gglib-mcp/src/builtin/mod.rs:158-164`), and the daemon composes every
run without a sandbox (`crates/gglib-runtime/src/compose.rs:111`). So the thing
a run most often lacks in the middle of a plan is not a file or a shell but a
fact only the person has: which branch, which of two files, whether to go on.

**What exists today.** A model that needs that fact either guesses or ends its
reply with the question in prose, and the person's next turn is the answer.
That is already "ask and wait": the next turn rebuilds the history from the
chat's rows (`saved_history`,
`crates/gglib-core/src/domain/agent/transcript.rs:73-83`, called at
`crates/gglib-axum/src/handlers/agent/hub_turn.rs:202-206`) and the model
reads its own question followed by the person's words as a user message.
Nothing is held while the person thinks. What the free form lacks is a mark
that says the reply is waiting on the person rather than finished, so no
composer can say "Answer", and the model gets the answer as a user turn rather
than as the result of the call it made, with the other calls of that batch
left unmade.

**Where a wait could live, and why it cannot.** Every mechanism a run has for
waiting is bounded, and each bound was written on purpose:

- A tool call runs under `tokio::time::timeout(config.tool_timeout_ms)`
  (`crates/gglib-agent/src/tool_execution/mod.rs:78-89`), default 30,000 ms
  and clamped to at most `MAX_TOOL_TIMEOUT_MS_CEILING = 60_000`
  (`crates/gglib-core/src/domain/agent/config.rs:29-33, 301, 451-452`), whose
  comment reads "Prevents a crafted request from holding server connections
  open indefinitely via slow or stalled tool calls." On expiry the model is
  told the tool timed out and keeps generating (`mod.rs:82-104`). A tool that
  waits for a person cannot be an ordinary tool call under that ceiling, and
  the ceiling is not to be raised for it.
- A run holds its model for its whole life. The hold is taken at
  `crates/gglib-axum/src/handlers/agent/run.rs:116` and
  `hub_turn.rs:147`, moved into the work future as `_hold` at `run.rs:210`,
  and released only when that future returns or is dropped
  (`run_hold_tests.rs:137-178`). While held, the resident is never evictable
  (`crates/gglib-runtime/src/process/admission/state.rs:509-513`), a recycle
  or relaunch is refused with a 503 naming "an agent run"
  (`admission/hold.rs:54-68`), and a request for a model that cannot
  co-reside waits for `ADMISSION_DEADLINE`, three minutes of no queue
  progress (`admission/timing.rs:78`), then gets a 503 that names the waiting
  model and not the holder (`residency/mod.rs:320-329`;
  `admission/README.md:81-83`). The queue's own text calls an in-flight count
  pinned that long "a hog or a wedge" (`admission/README.md:63-66`). Nothing
  releases a hold mid-run: `AdmissionLease` is `Drop`-only and not `Clone`
  (`crates/gglib-core/src/ports/model_runtime.rs:188-240`), and the loop's
  adapter is bound to one port at compose time
  (`crates/gglib-runtime/src/ports_impl/llm_completion/builder.rs:54-56`), so
  a hold released and re-taken after a swap has no path.
- A run holds one of four agent permits (`crates/gglib-axum/src/config.rs:56`;
  `run.rs:202`), one of `MAX_RUNS = 32` registry cells, which `make_room`
  evicts only once ended (`crates/gglib-app-services/src/runs/registry.rs:27,
  57-75`), and the conversation's live-reply lock, a 409 `conflict` for every
  other turn until the run is settled (`runs/admit.rs:69-78`;
  `registry.rs:50-55`). The registry is memory only; a restart loses every
  run (`runs/README.md:5-8`).

A run parked on a question with the hold kept would be the first unbounded
hold in the system; one parked with the hold released would need the
re-acquire path that does not exist, and would still keep a registry cell and
the chat's lock for as long as nobody answered.

**What the wire can and cannot take.** `RunStatus` is five values
(`crates/gglib-core/src/domain/runs/wire.rs:23-34`), hand-mirrored in ggchat
with no fallback (`ggchat Sources/GGChatCore/Runs/Runs.swift:20-39`); a sixth
is read by a shipped phone as a refusal of the run
(`OpenAICompatibleProvider+Runs.swift:113-120`) and by the shipped web page
as a run that is not live (`src/hooks/useGglibRuntime/savedRows.ts:51-57`).
Unknown frame types are ignored by every reader: the daemon's row writer
(`crates/gglib-core/src/domain/agent/replay.rs:76-96`, `#[serde(other)]`),
the web (`src/hooks/useGglibRuntime/agentEventDispatch.ts:170-176`) and the
phone (`OpenAICompatibleProvider+HubTurns.swift:73-116`), which also means a
question sent as a new frame type is drawn nowhere and saved nowhere.

**What the rows already do.** A call without a result is saved as a tool row
reading `UNFINISHED_TOOL_CALL`, "The tool call did not finish: the reply
stopped first." (`replay.rs:68-74, 145-153`), and the last assistant row of a
run that did not complete carries `incomplete: true` (`replay.rs:273-288`). A
history ending in a tool message is the ordinary shape the loop starts from
after any batch (`crates/gglib-agent/src/agent_loop.rs:538-561`), and
`Message::to_agent_message` restores tool rows exactly
(`crates/gglib-core/src/domain/chat.rs:84-125`).

**Who a device's turn may call.** A device's turn gets no tools unless the
tunnel was enabled with `--allow-mcp` and the chat's settings name them
(`hub_turn.rs:256-261`), under [ADR 0012](0012-the-remote-tunnel.md)
decision 5 and ADR 0013's amendment of 2026-09-30, whose stated reason is
that a leaked key must not run a shell server. The agent adapter runs the
request pipeline (`crates/gglib-runtime/src/ports_impl/llm_completion/mod.rs:218`),
whose `strip_unsupported_tools` stage removes `tools` from a request to a
catalogue-resolved model that cannot call them
(`crates/gglib-core/src/request_pipeline/apply.rs:142`; `tools.rs:30`), and a
local upstream's context is resolved from the catalogue
(`crates/gglib-axum/src/handlers/agent/remote_upstream.rs:137-142`;
`request_pipeline/model_context.rs:126`), so a device's turn on a model that
takes no tools is sent none whatever is offered.

**Privacy.** "A frame's content and a request body never reach a log line, a
tracing field, an error message or the disk. Log ids, statuses, counts and
sizes." (`runs/README.md:38-41`). Three lines today would carry a question
if one arrived malformed: the stream collector's `raw_args` and `raw` warns
(`crates/gglib-agent/src/stream_collector.rs:405-416, 342-351`) and the web
dispatcher's `{ event }` warn (`agentEventDispatch.ts:72-101`).

**The scope of the evidence.** Everything above is read off the code at
`0fb0b5db`. Nothing is measured: no run has asked a question, so there is no
reading of how often a model would ask, how long an answer takes, or what the
answer's run costs. Each criterion below is written unread, with the
denominator it will have.

### Decisions

Fifteen decisions. The one sentence they add up to: a run that asks ends on
the question, saved as the chat's own rows, and the answer is the chat's next
turn, carried back to the model as that call's result. Nothing is held while
nobody answers.

#### 1. `builtin:ask_user` is one more built-in tool, and the tool layer learns nothing else

`BuiltinToolExecutorAdapter::all_definitions`
(`crates/gglib-mcp/src/builtin/mod.rs:52-83`) gains `ask_user`, whose schema
is one required string, `question`, and whose description is the whole of
what the model is told (decision 14). `list_tools` without a sandbox returns
every non-filesystem definition instead of the first one alone
(`mod.rs:158-164`), so a daemon run is offered `builtin:get_current_time` and
`builtin:ask_user`. The executor's arm for `ask_user` is a backstop that
returns an error, which the loop hands to the model as a failed tool result
(`tool_execution/mod.rs:84`): it is reached only by a call decision 2 did not
intercept. The qualified name is a constant beside `UNFINISHED_TOOL_CALL` in
`gglib-core`'s agent domain, because the loop and the row writer both name
it and neither depends on `gglib-mcp`. `format_tool_display_name` says
"Question" for it and `format_tool_args_summary` returns none
(`crates/gglib-core/src/domain/agent/tool_display.rs:73-108`), so no client's
one-line caption carries the first sixty characters of a question; the
question travels as the reply's text (decision 2).

#### 2. The loop ends its run on an ask, with the question as the reply's last text

In `AgentLoop::run` (`agent_loop.rs:377-451`), after the guards and before the
batch is executed, when the offered tools include `builtin:ask_user` and the
batch holds a call to it whose `question` is a non-empty string: every other
call in the batch runs as today, with its start and completion frames and its
results appended; the ask gets a `tool_call_start` and no completion; the
loop emits a `text_delta` carrying the question, on a new line when the turn
already had text, then `final_answer` whose content is the turn's text and the
question; it appends the assistant message and the other calls' tool messages
to the history, with no tool message for the ask, and returns `Ok` as
`finalize_answer` does (`agent_loop.rs:260-280`). The run ends `completed`
through `drive` (`runs/admit.rs:128-137`). Not intercepted, and so sent to the
executor and answered as a tool failure the model can read and retry: an ask
whose arguments carry no `question` string, and an ask when the tool was not
offered, which the filter refuses as it refuses any tool outside the session
(`crates/gglib-core/src/ports/tool_executor_filter/filtered.rs:95-100`). So a
malformed ask never ends a run.

`final_answer` and `text_delta` are reused rather than a frame type added,
and that is a decision: every shipped decoder shows the question because of
it. The phone reads `text_delta` and nothing else of a reply's end
(`OpenAICompatibleProvider+HubTurns.swift:93-112`), the web settles on
`final_answer` (`src/hooks/useGglibRuntime/drawRun.ts:93-109`), and the row
writer takes `final_answer` as the assistant row's content
(`replay.rs:264-268`). The frame's doc says what it now means: the reply's
settled text, which ends the loop, and a question the model asked is that
text.

#### 3. Replay saves the open question as the chat's own rows

The ask's `tool_call_start` becomes the assistant row's `metadata.tool_calls`
and the `final_answer` its content, as today (`replay.rs:236-288`;
`transcript.rs:21-63`). For a call that got no result, when the run completed
and the call is `builtin:ask_user`, the tool row's content is
`ASK_UNANSWERED`, "The person was asked and has not answered.", with metadata
`tool_call_id` and `unanswered: true`, and it is written after the turn's
other tool rows so it is the chat's last row. When the run did not complete,
a Stop or a shutdown landing between the ask's start frame and the
`final_answer`, the `UNFINISHED_TOOL_CALL` rule and the `incomplete` mark
stand unchanged. The rows of a reply are written all or none in `save_reply`
under `drive`'s end handler (`runs/admit.rs:144-148`;
`crates/gglib-axum/src/handlers/agent/transcript.rs:165-187`), so no Stop can
leave a question row without its assistant row. The question's text is saved
twice, both times as rows: in the assistant row's content and in its
`tool_calls` arguments. The duplicate is accepted so that a phone which drops
tool rows and metadata still shows the question
(`ggchat Sources/GGChatUI/AppModel+HubTurnImages.swift:121-128`).

#### 4. An open question is a chat whose last row is an unanswered tool row, and nothing else holds it

There is no run state, registry cell, status, timer or hold for a question.
The asking run is completed, settled and retained like any ended run
(`runs/cell.rs:20-25`), and `make_room` evicts it first. Its hold, permit
and lock went when its work future returned. The hub's chat list carries
one more optional key beside `live_run`
(`crates/gglib-core/src/domain/hub_chats.rs:32-35`;
`crates/gglib-app-services/src/hub_chats.rs:68-80`): `open_question`, the
`tool_call_id` of the unanswered placeholder when the chat's last row is one,
so a client that does not read tool rows learns the question is open from
the list it already reads, and the shipped phone's decoder passes the key
over (`ggchat Sources/GGChatCore/Hub/HubChats.swift:150-190`). This machine's
page reads the same fact off the rows it already loads. Any row written
after the placeholder closes the question: an ordinary turn's user row, an
edit or regenerate through `replace_from`, a CLI turn. A restart loses
nothing, because the daemon held nothing: a chat with an open question reads
exactly as a chat whose last reply ended with a question, which is what it
is.

#### 5. The answer is a turn that names the call it answers: one optional key, `answers`, on both doors' bodies

`HubTurn` (`crates/gglib-core/src/domain/hub_chats.rs:66-87`) gains
`answers: Option<String>` in the `thinking` key's form, defaulted and skipped
when none, so a shipped phone's body is unchanged and an old hub refuses a
new phone's answer as it refuses any unknown key (`deny_unknown_fields`,
`:73`). `AgentRunRequest` (`crates/gglib-axum/src/handlers/agent/dto.rs:208-240`)
gains the same key. On an answer, `content` is the person's answer to the
call `answers` names, and it must be non-empty; `images` must be empty, since
`AgentMessage::Tool` carries text alone
(`crates/gglib-core/src/domain/agent/messages.rs`); `replace_from` must be
absent; a local answer must name its conversation. Each refusal is
`400 invalid_request` with fixed text. No route, kind or status is added: the
body of `PUT /api/runs/{id}?kind=agent` and `PUT /v1/runs/{id}?kind=agent`
grows one key, and the proxy's pinned route list
(`crates/gglib-proxy/src/router_tests.rs:19-63`) is unchanged.

#### 6. Each door plans an answer as it plans a turn, with the answer in the tool result's place

The hub's door, `hub_turn::plan` (`hub_turn.rs:163-235`): after the live-run
check and the rows are read, when `answers` is set the chat's last row must
be the unanswered placeholder for that id, else `409 question_answered` with
fixed text, "The chat has no open question with that id: it was answered, or
the chat moved on; read the chat again." The history is the saved rows
without the placeholder, and the message pushed in the user message's place
(`hub_turn.rs:203-206`) is `AgentMessage::Tool` with that id and the answer.
This machine's door, `run::plan` (`run.rs:131-191`): the page sends the
history it builds from rows as for every turn
(`src/hooks/useGglibRuntime/wireMessages.ts:34-120`), ending in the tool
message for the ask, and the daemon requires that the last message is a tool
message whose id is `answers`, else `400 invalid_request`. Both reach
`launch` with the id. The loop then starts on a history ending in a tool
message, which is the shape it already starts from after any batch
(`agent_loop.rs:353-380, 538-561`): no resume path is added to the loop.

#### 7. The answer is written once, under the reservation, by replacing the placeholder with a user row

In `reserve_and_start` (`crates/gglib-axum/src/handlers/agent/launch.rs:68-141`),
with `answers` set, `save_answer` stands where `save_user` stands
(`:106-113`): it re-reads the chat's last row, which the reservation keeps
every other run off (`:99-101`), requires it to be the placeholder for
`answers`, else `409 question_answered` with the reservation dropped
unstarted and nothing written, and calls `replace_from` on the placeholder
(`crates/gglib-core/src/services/chat_history.rs:169`), one transaction,
with a user row whose content is the answer and whose metadata is
`answers: <tool_call_id>`, plus `device` for a paired device's answer as
`save_user` adds it (`crates/gglib-app-services/src/transcript.rs:109-115`).
The helper lives in `gglib_app_services::transcript`, the one writer of a
turn's rows, so the CLI saves through it too (decision 10). A repeated PUT
under the same run id finds the run and writes nothing (`launch.rs:90-98`):
the client-minted run id is an answer's idempotency key, as it is every
turn's. A second answer with a fresh id is `409 conflict` while the first's
run lives, and `409 question_answered` after. `record_model`,
`remember_thinking` and `save_reply` run unchanged.

#### 8. A user row carrying `answers` reads back as the call's result, in the one reading every surface shares

`Message::to_agent_message` (`chat.rs:84-125`) maps a user row whose metadata
has a string `answers` to `AgentMessage::Tool` with that id and the row's
content. `saved_history` therefore hands the hub's next turn,
`gglib chat --continue` and `hub_turn::plan` a history in which the model's
ask is followed by its result, and the web's `convertToWireMessages`
(`wireMessages.ts:34-120`) applies the same rule. A user row rather than a
tool row because of what shipped clients draw after the fact: the phone draws
user rows and drops tool rows (`AppModel+HubTurnImages.swift:121-128`;
`Role` has no tool case, `ggchat Sources/GGChatCore/Models.swift:3-7`), so a
phone that knows nothing of this shows the question as the Mac's text and the
answer as the person's own bubble; the web draws a user row as a user
message. The model's view and the person's view differ on purpose: the person
said it, and the model receives it where it asked.

#### 9. The ask is offered wherever any tool is offered, and to a device's turn without `--allow-mcp`

This machine's page appends `builtin:ask_user` to every non-empty tool filter
it sends (`src/hooks/useGglibRuntime/runRequest.ts:104-115`); `null`, which
means every tool, and `[]`, for a model known not to call tools, stay as they
are. `gglib chat` passes no filter and has every built-in
(`crates/gglib-cli/src/handlers/agent_chat/config.rs:164-193`). A device's
turn: `tools_of` (`hub_turn.rs:256-261`) returns `[]` when the chat says
`no_tools`, and otherwise `builtin:ask_user` always, plus `settings.tools`
when the tunnel is open to MCP. The plan test's "no tool, ever by default"
(`hub_turn_plan_tests.rs:40-50, 54-68`) becomes "the ask, and no other". The
gate stays what ADR 0012 decision 5 made it for every other tool, and this
one passes it for the reason the gate states: a leaked key must not run a
shell server, and `ask_user` runs nothing on the hub. Its only effect is a
question in the hub's own chat, which the hub's owner reads; a forged turn
that asks a question is a turn that asks a question. A device's turn whose
model cannot call tools is sent none, by the pipeline's strip stage
(`apply.rs:142`; `tools.rs:30`) on the catalogue-resolved context the local
upstream carries (`remote_upstream.rs:137-142`). No knob is added: the chat's
existing `no_tools` is the off switch on every surface, and today only the
CLI's `--no-tools` writes it (`crates/gglib-cli/src/commands.rs:134, 222`).

#### 10. The CLI's chat answers at its own prompt; `gglib run` is unchanged

`gglib chat` runs the loop in-process
(`crates/gglib-cli/src/handlers/agent_chat/repl.rs:237-289`), so an ask ends
the turn as decision 2 says, the drain prints the question as the reply's
text (`drain.rs:77-109`), and `run_single_turn` returns a history ending in
an assistant message whose last call has no result. The REPL reads that
(`repl.rs:153-200`): the next line is read under the prompt "Answer: "
instead of "You: ", it is sent as the tool message for that call, an `/image`
line is refused with "an answer is text alone", and the answer is saved
through the same `transcript::save_answer`, so a chat continued from the page
reads the same rows. `--continue` loads the rows by decision 8. Ctrl+C at the
"Answer: " prompt returns to it; `/quit` leaves the question open in the rows.
`gglib q` is one-shot: an ask prints the question and ends the turn, and only
the terminal's "Continue chatting?" hand-off into the REPL
(`crates/gglib-cli/src/handlers/inference/agent_question.rs:276-292`) can
answer it. `gglib run show` prints only a chat run's deltas
(`crates/gglib-cli/src/handlers/run/text.rs:5-14`) and shows nothing of any
agent run today; this decision widens no gap there and closes none.

#### 11. Each client shows the open question from the rows and answers through its composer; nothing live changes

The web: `buildLoadedMessage`
(`src/hooks/useChatPersistence/buildLoadedMessage.ts:20-60`) folds the
placeholder into the ask's tool-call part as it folds every tool row, a
renderer for `ask_user` (`src/services/tools/builtinIntegration.ts:60-66`)
draws the part as the question, and when the chat's last row is unanswered
the composer's placeholder reads "Answer" and Send builds the body with
`answers` and the history of decision 6, through `beginSend` as any send
(`src/hooks/useGglibRuntime/useGglibRuntime.ts:154-166`); no run is live, so
it is clear to send. The live reader needs nothing: `final_answer` settles
the reply and the end replaces drawn messages with saved rows
(`src/hooks/useGglibRuntime/useRunReader.ts:141-177`). ggchat, in its own ADR
dated with this one: `HubMessageMetadata` gains `toolCallID` and `unanswered`,
`HubTurn` gains `answers` encoded only when set, as `thinking` is; the hub
chat list's `open_question` and the opened chat's rows say when the field
reads "Answer" and the send carries `answers`; `409 question_answered` is one
line, "That question was already answered on <Mac>.", and the rows are read
again; a `400 invalid_request` on a turn that carried `answers` is "The gglib
on <Mac> needs updating before it can take an answer.", in the
`takesNoImages` pattern (`OpenAICompatibleProvider+HubTurns.swift:37-40`),
after which the phone sends the text as an ordinary turn. The composer's
Stop-only rule while the Mac writes
(`ggchat Sources/GGChatUI/HubChatComposer.swift:67-69, 93-111`) is unchanged:
nothing is writing while a question is open.

#### 12. An ordinary message while a question is open closes it, and is refused by nothing

A turn without `answers` on a chat whose last row is unanswered is an
ordinary turn: `save_user` appends the user row
(`crates/gglib-app-services/src/transcript.rs:98-120`), the placeholder
stays, and the model's next history reads its own ask, "The person was asked
and has not answered.", and then what the person wrote, as a user message.
That is coherent, and it is what every shipped client does today, so a hub
updated before its phones degrades to exactly this with no error. There is no
"dismiss" and no "say something else instead": on a client that knows the
feature whatever is typed is the answer, "forget that, do X" included, and on
one that does not it is a message that closes the question.

#### 13. Who may answer is who may add a turn, and the first answer wins by the row

ADR 0013's amendment of 2026-09-30 says a run on one of this machine's chats
belongs to the chat and every paired device may add a turn; an answer is a
turn, so this machine's page, its CLI and every paired device may answer a
question on a hub chat, each identified as the proxy identifies a turn
(`crates/gglib-proxy/src/runs/scope.rs:1-38`), which stays "a courtesy of
the API, not a boundary": an answer is as trustworthy as a turn. Two answers
race on the reservation (decision 7). The answer row carries `device` when a
paired device gave it, so the rows say who answered; the model's tool message
does not. A device's own chat run and the page's unsaved run have no rows and
so no answerable question: an ask there ends the run with the question in the
run's log alone (*Out of scope*).

#### 14. The model learns of the tool from its definition alone, and the person is its only bound

The daemon injects no system text about tools
(`crates/gglib-runtime/src/ports_impl/llm_completion/body.rs:90-104`), so the
description is the whole instruction: "Ask the person one question and stop
until they answer. Use it only when you cannot continue without their
decision or information; what they already said is in the conversation. Ask
one thing at a time: your reply ends when you ask, and their answer comes
back as this tool's result." The CLI's `gglib q` system prompt, the one place
tools are named in a prompt (`agent_question.rs:29-34`), gains the name. An
ask ends the run, so the loop detector never sees two asks in one run and
`Guards` are fresh per run (`agent_loop.rs:366`); nothing in the daemon
bounds a model that asks every turn, and nothing needs to, because the bound
is the person: a model cannot spend the GPU by asking, only by being
answered, and each answer is one turn the person chose to send. A repeat
asker is read, not guarded (criterion 5). Each answer's run starts with a
fresh iteration budget (`DEFAULT_MAX_ITERATIONS = 25`, `config.rs:53`), so a
task's iterations are bounded per answer, not per task.

#### 15. Errors are fixed sentences with codes, the rows are the only persistence, and no line carries a question

New codes: `question_answered` (409) with the sentence of decision 6;
`invalid_request` (400) with "an answer is text alone", "an answer is not
empty", "an answer names its conversation", "an answer's last message is the
tool result it carries". None echoes content, as the runs handlers require
(`crates/gglib-proxy/src/runs/handlers.rs:1-5`). The phone prefixes the hub's
name as it does for every run notice, which is how the error names the
machine to look at. The question and the answer live in the chat's rows and,
while the asking run is retained, in its in-memory log as frames, the same
place every reply's text lives. Three lines that could carry a question are
reduced to types and lengths in the same change: the stream collector's
`raw_args` and `raw` warns (`stream_collector.rs:405-416, 342-351`) and the
web dispatcher's `{ event }` warn on a malformed `text_delta` or
`tool_call_start` (`agentEventDispatch.ts:72-101`). The wire, in sum: no
frame type, status, route or kind; two optional body keys (`answers` on each
door), two metadata keys (`unanswered` on a tool row, `answers` on a user
row), one list key (`open_question`), one error code. Recorded:
`contracts/chats/recorded.json` gains an answer turn, written by
`hub_chats_tests.rs` and hand-copied into ggchat as the others are;
`turn_made.json`'s recorded turn gains an ask so the placeholder row is
pinned; `contracts/runs/recorded.json` is unchanged.

### Consequences

- **Good:** a person can be asked mid-plan from any device that reads the
  chat, and the plan is intact on the answer in the only sense a run ever
  had: the model's own ask and the person's answer are the rows every surface
  rebuilds history from, and the other calls of the batch were run and saved
  before the question. The loop needs no resume path.
- **Good:** nothing waits anywhere. No hold, permit, lock or registry cell is
  kept while a question is open, so the tool ceiling, the admission deadline,
  the watchdog's refused recycle (`crates/gglib-proxy/src/server.rs:894-919`),
  `MAX_RUNS` and the four permits are untouched; a restart loses nothing;
  `gglib run list` shows no parked run because there is none. The GPU is spent
  only by a person's turn, which is
  [ADR 0006](0006-recover-dont-predict.md)'s rule kept by construction.
- **Good:** zero wire breakage. A shipped phone shows the question as text and
  its own answer as its own bubble; a shipped hub answers a new phone with one
  fixed notice, after which the phone sends an ordinary turn.
- **Cost, accepted:** the answer's run is a fresh admission. Where a parked run
  would have kept the model resident, this one relies on llama-server's prompt
  cache when the model stayed and the prefix is unchanged, and otherwise pays
  a swap back and a cold prefill of the whole chat
  (`residency/mod.rs:115-253, 438-505`): on a large model with a long chat,
  tens of seconds between the answer and the first token. Criterion 4 reads
  it, and criterion 6 reads whether a hold would ever have mattered.
- **Cost, accepted:** the person's words reach the model as a tool result,
  not a user message, and a model that weighs tool output below the user may
  weigh "no, the other branch" differently for it. Nothing proposed measures
  that.
- **Cost, accepted:** every device turn on a chat that does not say
  `no_tools` now sends one tool where today it sends none, and the only writer
  of `no_tools` is the CLI. A device turn on a passthrough model, one the
  catalogue did not resolve, is not protected by the strip stage; a hub chat's
  model is a catalogue model (`hub_model.rs:47-88`), so that case is not
  reachable from a device's turn today, and criterion 3 is where it would
  show if that changes.
- **Cost, accepted:** `final_answer` is emitted for a reply the model did not
  finish and `text_delta` carries a sentence it did not stream. A reader that
  counts `final_answer` frames as finished replies counts asks among them.
- **Cost, accepted:** the question text is saved twice, both times as chat
  rows.
- **Stated plainly, because it will surprise people:** an open question is
  closed by any message, and nothing tells a person on an old client that
  their message went in beside an unanswered question rather than as its
  answer.
- **Stated plainly:** the free form already did most of this. What the tool
  adds is the mark that a reply is waiting, the composer that knows it, the
  answer returned where the model asked, and the rest of the batch run before
  the question. If criterion 1 shows people do not come back to a question
  that ended a reply, the tool goes and the free form stays.
- **Stated plainly:** `gglib run show` prints nothing of an agent run today
  and still does not; CLI parity for asking is `gglib chat`'s "Answer: "
  prompt. A question asked on a run with no conversation ends the run and is
  forgotten with it.
- **Stated plainly:** during the answer's run the model is held as during any
  turn, and a Copilot request for another model behind it still gets the
  stall 503 that does not name the holder (`admission/README.md:81-85`). This
  decision neither widens nor closes that gap (*Out of scope*).
- **Bookkeeping:** `turn_made.json` and `contracts/chats/recorded.json` are
  regenerated on this side and `gglib-chats-recorded.json` re-copied into
  ggchat by hand (`ggchat Tests/GGChatCoreTests/HubChatsWireTests.swift:5-7`);
  ggchat's own agent-frame fixture gains an asking turn by hand, since no
  shared contract for frames exists.

### Kill criteria

Every reading below is taken on the hub, from the chat's rows in its database
at `<data root>/data/gglib.db` (`crates/gglib-core/src/paths/database.rs:26`),
with `sqlite3` over `chat_messages`; an ask is an assistant row whose
`metadata.tool_calls` names `builtin:ask_user`, and the denominator of each
share is every ask on that hub since the feature landed, stated with the
reading. A zero is recorded with that denominator. None has been taken.

1. **Unanswered share.** Tool rows with `unanswered: true` (questions never
   answered, or closed by an ordinary message) over asks. If, with at least
   20 asks, more than half remain unanswered, decision 2 is reopened: people
   do not come back to a question that ended the reply, and the tool leaves
   the default offer (decision 9) rather than being patched with a timer.
2. **Closed-by-message share.** User rows whose preceding row is an unanswered
   placeholder and whose metadata has no `answers`, over asks, taken only
   after the web page and the ggchat ADR have both shipped, which the reading
   names. If more than 1 in 5 asks are closed this way, decision 12 is
   reopened in favour of a composer that refuses, or confirms, an ordinary
   message while a question is open.
3. **Malformed-ask share.** Tool rows whose content begins with the executor's
   fixed backstop text (decision 1), over that count plus asks: every attempt
   to ask. If above 1 in 5, small models are confused by the tool and decision
   9's default offer to device turns is reopened. A device turn that fails
   `agent_error` on a model sent a `tools` array it could not take shows here
   first as an `incomplete` assistant row with no tool rows after a device's
   user row; that count has no clean query and the gap is named.
4. **Cold-prefill cost.** For each assistant row that directly follows a user
   row with `answers`, the `cachedTokens` and `promptTokens` the run's
   `turn_usage` wrote (`replay.rs:36-50`), over answer runs. If in more than
   half of them `cachedTokens` is under half of `promptTokens` on the owner's
   own machine, "nothing parks" is paying a full re-prefill per answer, and a
   bounded hold during the wait is reopened as a new ADR, not an edit to this
   one.
5. **Repeat-asker share.** Consecutive asks on one chat whose `question`
   arguments are byte-identical, over asks. If above 1 in 10, decision 14's
   "the person is the only bound" is reopened for a guard or a changed
   description.
6. **Answer latency.** The gap between the placeholder's `created_at` and the
   answering user row's `created_at`, over answered questions, as a median.
   This one reverses nothing by itself: it is the reading that says whether
   the alternative this entry declined would ever have paid. A median under a
   minute, beside criterion 4 firing, is the case for a bounded hold; a median
   in hours closes the question with a number.
7. **Issue tracker.** `gh issue list --label "component: axum"` on this
   repository, read against this entry's date. The issue form offers no
   `component: runs` or `component: agent` label, so the query returns more
   than this feature, and naming that gap is part of the reading. Two open
   issues from different weeks describing a question lost, answered twice or
   answered into the wrong place reopen decision 7's replace-the-row write.

### Out of scope

- **A time limit on an open question, or a sweep of placeholders.**
  Considered and declined: an open question costs the daemon nothing
  (decision 4), and
  [ggchat ADR 0006](https://github.com/mmogr/ggchat/blob/main/docs/adr/0006-a-send-waits-for-its-pipe.md)
  chose no limit for a wait that stores nothing. Criterion 1 is what would
  add one.
- **Holding the model, permit or lock while the person answers, with the ask
  waiting inside the tool call.** The two alternative designs, declined below.
  Criteria 4 and 6 are what would bring a bounded version back, as a new ADR.
- **Typed, multiple-choice or structured answers, and images in an answer.**
  An answer is text alone because `AgentMessage::Tool` carries text alone; a
  later ADR may add choices to the schema.
- **A dedicated answer route, run kind or status.** Declined: `kind` and the
  route list are shipped contracts, and a turn already carries everything an
  answer needs but one key.
- **A question over the plain proxy chat (`/v1/chat/completions`) or a chat
  run (`gglib run start`).** Neither runs the loop, so neither can ask.
- **Asking from `gglib q` when stdin is not a terminal or `-Q` is set.** The
  question is printed and the turn ends, as any reply does there.
- **`gglib run show` rendering agent-run frames, a question included.** A
  pre-existing parity gap this entry neither widens nor closes.
- **A question on a run with no conversation.** A device's own chat run and
  the page's unsaved run have no rows; the question ends the run and is
  forgotten with it (decision 13).
- **Re-emitting a question after a daemon restart.** The rows are the record
  and the client reads them.
- **A loop-guard change for the ask.** Nothing to guard: an ask ends the run.
  Criterion 5 reads the repeat asker instead.
- **Telling the model who answered.** The answer row carries `device`; the
  model's tool message does not.
- **Other MCP servers' own ask-style tools.** They stay ordinary tool calls
  under the ceiling.
- **The stall 503 naming the held model.** A Copilot request that waits behind
  the answer's run, or any run's, is told "the queue made no progress while
  '<model>' waited" (`residency/mod.rs:325-328`), and the admission README
  records the gap (`README.md:81-85`). Naming the holder is a change to
  admission's error text that this feature neither needs nor should carry; a
  sentence of the shape "'<waiting>' waited while '<held>' is held by an
  agent run on this machine; stop that run, or wait for it to end" belongs to
  its own change.
- **A `gglib serve` pin that names a model other than the chat's.** The
  answer's turn then fails `model_unavailable` (`hub_model.rs:157-163`) as any
  device turn does under a pin today; the text names nothing and that is a
  pre-existing gap of its own.

### Alternatives considered

| Design | What it does while nobody answers | Why it lost |
|---|---|---|
| Park, keep the hold, bound the wait at five minutes | Keeps the model, a permit, a registry cell and the chat's lock; ends the run `failed` when the bound passes | Pins a GPU model for a person's silence, which the queue's own text calls a hog after three quiet minutes; the bound is a number for a hypothetical, chosen by analogy to a silent server; after it the person gets the free form plus a failed run. Most surface of the three: a new port into the loop, a `select!` rewrite of `work`, a new route, a changed 503. |
| Park, release the hold, re-admit on the answer | Frees the model; keeps a registry cell and the chat's lock with no clock; re-admits the model when the answer comes | Needs the re-acquire path that does not exist: a rebinding adapter URL, a mutex-held optional lease and permit, a third joined future, a `model_gone` failure. Thirty-two parked questions refuse every new run on the daemon, and a key-holder can park them on purpose. A run-triggered `admit` on resume is GPU spend the run's machinery starts. |
| The ask ends the run (this entry) | Nothing | Pays the swap and the cold prefill at the answer instead of holding through the wait, and reuses `final_answer` for a reply that is not final. Both named above and read by criteria 4 and 6. |
