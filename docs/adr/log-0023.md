# ADR 0023 log

[ADR 0023](0023-a-chats-folder-is-where-gglibs-own-file-tools-read.md) log.
Readings, measurements and follow-up bookkeeping, appended and never edited;
a line number refers to the commit the entry names. Its first three entries
are the arc's readings and interim decisions, appended while the arc was

## 2026-10-22: the arc opens, and the file tools are hardened before they widen

The arc's decision, in short: a chat's folder is where gglib's own file
tools read. It is the directory `gglib chat` was launched in, the folder the
page chose, and none for a paired device. The folder is a property of the
chat run and reaches the three builtin file tools, `builtin:read_file`,
`builtin:list_directory` and `builtin:grep_search`, as their per-run sandbox
root, and nothing else: external MCP servers keep their static arguments and
`working_dir`. The model is told its folder in the three tools' own
descriptions, per run, and no system prompt changes. No new setting, flag,
route, table or protocol feature is added.

The arc starts from one report, from one user and one run: the GUI's
"Filesystem Access" template saves the placeholder path `/path/to/allowed`,
the server it starts exits before any handshake, and that chat went on with no
file tools and only `Server closed connection` in the log. At `843047f5` the
builtin tools already exist, and only `gglib q` gives them a root, its
working directory (`crates/gglib-cli/src/handlers/inference/agent_question.rs:98`);
the daemon composes every run with none (`crates/gglib-runtime/src/compose.rs:143`).
Whether a small model does better when told its folder is unmeasured.

This entry's change is the arc's first, `fix(builtin): the file tools stay
inside their folder, accept an absolute path inside it, and say where a miss
was`. Before the tools reach more surfaces than `gglib q`, it closes what the
read at `843047f5` found in them:

- **An absolute path inside the root was rebased under it.**
  `resolve_sandboxed_path` stripped every absolute path's root
  (`crates/gglib-mcp/src/builtin/sandboxing.rs:32-41`), so a model that named
  `<root>/x` was told it did not exist. An absolute path under the root, as
  given or canonical, is now taken as is; any other absolute path is still
  rebased, and the canonical containment check (`sandboxing.rs:52`) is
  unchanged.
- **A refusal said "sandbox" and echoed the host path.** A miss now reads
  `No file or folder '<path>' in the working folder. Call list_directory to
  see what is there.` and an escape `'<path>' is outside the working folder.`,
  with the path as the model wrote it, or its part under the root; the three
  tools' other refusals name it the same way. A path that exists but cannot
  be read says why instead of that it is missing. The two endings are the
  constants `MISSING` and `OUTSIDE` in `sandboxing.rs`, the phrases the arc's
  first kill criterion will count in tool rows.
- **`grep_search` followed a symlink out of the root.** `walk_dir` tested
  `path.is_dir()` (`crates/gglib-mcp/src/builtin/fs_grep.rs:136`), which
  follows links, and never rechecked containment. It now reads each entry's
  own type and follows a link only when its canonical target lies under the
  canonical root. A link to `.` or to an ancestor was walked again until the
  kernel's link limit, about 40 levels, listing every match once per level;
  a folder already on the walk's way down is now not entered again.
- **`read_file` could panic on a long file.** It cut at byte 100,000
  (`crates/gglib-mcp/src/builtin/fs_read.rs:38`), which can fall inside a
  character. It now keeps the first 100,000 characters.
- **The tool timeout could not end a walk.** The three tools ran inline on
  the async executor (`crates/gglib-mcp/src/builtin/mod.rs:320`). They now
  run under `spawn_blocking`, and a guard dropped with an abandoned call sets
  a flag that `walk_dir` checks before each entry.

The changes that follow, in order on one line of the stack: the three tools'
descriptions name their folder and the page's tool picker stops listing them;
a chat gets its folder on the CLI, the daemon and the page; and the ADR
closes the arc. Beside that line, on `main`: a server that fails to start
says what it printed, and the "Filesystem Access" template is dropped.

## 2026-10-22: the file tools name their folder, and the page's tool list stops carrying them

This entry's change is `feat(builtin): the file tools name their folder, and
the picker stops listing them without one`. At `843047f5` no file tool's
description named its folder (two said a path "is relative to the working
directory"), and `GET /api/builtin/tools` listed all three, so the page's
Tools popover offered three tools that no daemon run could use: the daemon
composes each run with no root, and a tool that needs one is not offered.

- **The model is told its folder in the three tools' own descriptions.**
  `Builtin.definition` takes the sandbox root
  (`crates/gglib-mcp/src/builtin/mod.rs`), and each file tool's description
  ends ``The working folder is `<root>`; a path is relative to it.``, the
  root in backticks with any control character in it escaped, built when
  the tools are listed and never stored. `get_current_time` and
  `generate_image` ignore the root. Today only `gglib q` passes one, so
  only its descriptions change; no system prompt is edited.
- **The page's list holds only what needs nothing from the run.**
  `bare_definitions` leaves out a tool that needs the root as it already left
  out the one that needs a drawing tool, so the route answers with
  `get_current_time` alone, and the Tools popover changes with no page code.

## 2026-10-23: a chat has a folder, on the CLI, the daemon and the page

This entry's change is `feat(chat): a chat has a folder: the CLI's is where
it ran, the page's is chosen, a device's is none`. Before it only `gglib q`
gave the file tools a root; now every chat surface decides one, and the
rules that make one live in `crates/gglib-core/src/domain/folder.rs`:
`launched` (:33) for a directory a session ran in, never home or `/`, and
`chosen` (:51) for a path a person named, absolute and a folder. Either
answers a canonical path, so the folder shown is the folder read.

- **The CLI's folder is where it ran.** `gglib chat` reads the directory it
  was launched in, every invocation, `--continue` included
  (`crates/gglib-cli/src/handlers/agent_chat/files.rs:20`), and passes it to
  `compose_agent_loop`'s new `sandbox_root` (`crates/gglib-runtime/src/compose.rs:131`).
  It says so once on stderr: `Files: <dir> (read-only)`, with `on this
  machine (read-only; what is read is sent to <machine>)` under `--remote`
  (`files.rs:77`). A `--tools` list keeps the file tools only when it names
  one, bare or as `builtin:<name>` (`files.rs:62`); a list that names none
  gets no folder, no line, and its directory is not read. The CLI never
  writes `ConversationSettings.folder`: a folder the page chose for the same
  chat survives a `--continue` unread, since the resume keeps every setting
  it does not set (`resume_machine_tests.rs`,
  `a_remembered_thinking_choice_and_folder_survive_a_resume_on_another_model`).
- **The page's folder is chosen and remembered.** `ConversationSettings`
  gains `folder` (`crates/gglib-core/src/domain/chat.rs:332`), written only by
  `record_folder` (`crates/gglib-core/src/services/chat_history.rs:129`).
  `PUT /api/runs/{id}?kind=agent` takes `folder` (`dto.rs:316`): a path
  sets it, `""` forgets it, absent runs as remembered; without a
  `conversation_id` a path is that run's alone. `settle_folder`
  (`crates/gglib-axum/src/handlers/agent/run.rs:233`) refuses before
  anything is written: **400 `folder_unusable`** for a said path that is
  relative, missing or not a folder, the message naming the path as said;
  **409 `folder_missing`** for a remembered folder gone since, which only
  saying another folder or `""` gets past. `""` is never checked, so a gone
  folder can always be cleared. The conversation then remembers the
  canonical path (`launch.rs:186`). A list that names tools gains the three
  file tools when the run has a folder (`compose.rs:151`); `[]` stays `[]`.
- **A device's turn has no folder.** `hub_chats::open()` strips
  `settings.folder` from what a device reads
  (`crates/gglib-app-services/src/hub_chats.rs:98`), `hub_turn::plan` writes
  none (`hub_turn.rs:328`), and a device's turn is composed by
  `held_for_device` (`hub_turn.rs:201`) with `None`, whatever its chat
  remembers: ADR 0012 decision 5 grants a device this machine's tools only
  through `--allow-mcp`, which names no file tool.
- **The GUI.** The composer's `FolderChip` beside Thinking, driven by
  `src/hooks/useChatFolder.ts`: the native dialog on desktop, a typed path on
  web, Change and Clear, and the 400/409 error state. Its titles say where
  the folder is (this machine on desktop, "the machine gglib runs on" on
  web), and, for a chat on the paired machine's model, that what is read is
  sent to that machine's model, as the CLI's `--remote` line does
  (`FolderChip.tsx:15`, `:21`).

Where the code departs from the decision's text, with why:

1. **The chip stays visible for a model that calls no tools when the chat
   already remembers a folder** (`useChatFolder.ts:160`). The decision hides
   it then. Hidden, a no-tools model on a chat whose folder is gone would be
   refused 409 with nothing on the page to clear it with. Its title says
   the folder is not read by this model (`FolderChip.tsx:21`).
2. **The 409 is returned even when the run's tool filter is `[]`**
   (`run.rs:254`), although `with_folder` keeps `[]` and that run would not
   read the folder. Kept strict on purpose: the chip is shown in that case
   (item 1), and a chat that silently goes on remembering a folder that is
   gone would surprise the next model that calls tools.
3. **`admits_a_file_tool` and the `Files:` line live in a new
   `agent_chat/files.rs`**, not beside `tool_filter` in `config.rs` and in
   `mod.rs`: `config.rs` is already at 402 lines, and `mod.rs` grows by five.
4. **The CLI reads its directory only when the list admits a file tool**
   (`files.rs:20`), and a directory that cannot be read, deleted since the
   shell entered it, is no folder: the session starts and says `Files: off;
   the folder this ran in cannot be read (...)` (`files.rs:31`). The
   decision read `current_dir()?` first, which would have refused to start
   any `gglib chat` there, `--no-tools` included, after its conversation row
   was made.
5. **The refusal line names both places**: `Files: off in your home folder
   or /; cd into a project to read it, or --no-tools` (`files.rs:77`). The
   decision's wording named only the home folder, which is false for `/`.
6. **A said path whose canonical form is not UTF-8 is refused 400
   `folder_unusable`, and only when a conversation will remember it**
   (`run.rs:246`): `ConversationSettings.folder` is an `Option<String>`, so
   such a path cannot be stored; a run with no conversation reads it as is.
7. **`with_folder` runs before `with_drawing`** (`compose.rs:237`). Reversed,
   `[]` sent with Draw would become a list that names a tool and so gain the
   file tools, for a model that calls no other tool.
8. **The names of the file tools have one source**, `gglib_mcp::FILE_TOOLS`
   (`crates/gglib-mcp/src/builtin/mod.rs:33`), which the builtin table names
   its rows from and a test pins to its `needs_sandbox` rows; the CLI's
   predicate and the daemon's `file_tools()` (`compose.rs:141`) read it.
   The decision had each crate list them.
9. **`late_on` is split** (`hub_turn.rs:179`): after the model is found it
   resolves the upstream and calls `held_for_device`, so the test that a
   device's turn on a chat with a folder is offered no `builtin:read_file`
   drives the production step that passes `None`
   (`run_folder_tests.rs`,
   `a_devices_turn_on_a_chat_with_a_folder_is_offered_no_file_tool`).

Known and left as is:

- **The page shows an accepted path as said until the next reading.** After
  a run accepts a typed or picked path, the chip shows that path, which may
  be a link or end in a slash, until the chat page's refresh after the send
  reads the conversation and shows the canonical path the daemon recorded
  (`useChatFolder.ts:170`).
- **On Windows the recorded folder is a verbatim `\\?\C:\...` path**, from
  `Path::canonicalize` (`folder.rs:33`, `:51`); it is shown in the chip's
  title, the CLI's line and the three tool descriptions. Containment holds,
  as `sandboxing.rs` already canonicalises the same way; only what is shown
  is affected.
- **Where the end-to-end check stopped.** In review of this change's first
  cut, driven against a live daemon with a fresh data dir, every refusal above was returned as listed and wrote
  nothing; a said folder that passed `settle_folder` was then refused at
  `remote_upstream::resolve`, which wants a llama-server the daemon started,
  so recording the canonical path, reusing it and two concurrent roots were
  checked only by `run_folder_tests.rs`. The CLI was driven against a fake
  OpenAI-compatible server: each `Files:` line, the tools offered, the
  folder in their descriptions, a `read_file` inside it, and a GUI folder
  surviving `--continue` unread. The page was not driven in a browser.

## 2026-10-23: the arc closes, and ADR 0023 is written

This entry's change is `docs(adr): 0023 a chat's folder is where gglib's own
file tools read`. It writes
[ADR 0023](0023-a-chats-folder-is-where-gglibs-own-file-tools-read.md) from
the three entries above and the arc's design, read at `508bb2d1`, the head
of the arc's line. Where an entry's departure from the design changed what
the code does, the ADR states the code: the refusal line names home and `/`,
the CLI's folder lives in `agent_chat/files.rs`, `with_folder` runs before
`with_drawing`, the file tools' names have one source in `FILE_TOOLS`, a 409
is returned whatever the run's tool filter, a non-UTF-8 path is refused only
when a conversation would store it, and the chip stays for a model that calls
no tools while its chat remembers a folder.

Two changes of the arc are made on `main` by their own commits, beside the
line, with no entry here:

- **`fix(gui): drop the Filesystem Access template`.** The template whose
  placeholder path started the arc is gone from the Add MCP Server picker,
  and a line under the grid says reading files is built in. ADR 0023's
  decision 8.
- **`fix(mcp): a server that fails to start says what it printed, and the
  CLI shows it`.** The MCP client keeps the last 4 KiB a server printed on
  stderr (`crates/gglib-mcp/src/stderr_tail.rs`), read in a task, or on a
  thread of its own on Windows; a closed connection ends ` - stderr: <tail>`;
  `prewarm_lazy` returns each lazy server it could not start or found
  invalid, and `gglib chat` and `gglib q` print one stderr line each unless
  `-Q`. ADR 0023's decision 9.

This change also links ADR 0023 from the modules it governs:
`crates/gglib-core/src/domain/folder.rs`, `crates/gglib-mcp/src/builtin/`,
`crates/gglib-axum/src/handlers/agent/`,
`crates/gglib-cli/src/handlers/agent_chat/files.rs`, the page's
`useChatFolder` row in `src/hooks/README.md`, and by name the device strip in
`crates/gglib-app-services/src/hub_chats.rs` and `compose_agent_loop`'s
`sandbox_root` in `crates/gglib-runtime/src/compose.rs`. `docs/cli.md`
gains that an added MCP server runs once per gglib process and every chat in
that process shares it, as decision 1 says.

Follow-ups, none of which this change takes:

- **The two-suite reading ADR 0023's Context names has not been taken.** It
  needs a model on the owner's machine. Two suite files, each a JSON array of
  tasks in the shape of `crates/gglib-core/assets/tune_default_suite.json`, with
  tools named `read_file`, `list_directory` and `grep_search` and identical
  tasks, differ only in the tools' descriptions: one ends each with the text
  the tools are listed with under a root, ``The working folder is `<root>`; a
  path is relative to it.`` (`crates/gglib-mcp/src/builtin/mod.rs:210` at
  `508bb2d1`), the other with the text without one, ``A path is relative to
  the working folder.`` (`:196`). Each runs once:

  ```
  gglib benchmark agentic --model <model> --task-suite <folder-named.json>
  gglib benchmark agentic --model <model> --task-suite <folder-unnamed.json>
  ```

  with the default three seeds and the default A/A pair and control, and is
  read from the report each run prints as it ends: the `gglib` arm's
  composite, and the `A/A:` line's gap as that run's drift. It scores only
  whether the calls carry the paths the tasks' `required_args` expect, with
  no filesystem behind them, and the eval's A/A drift is per run, so the two
  runs are compared by hand against the larger of their two drifts. A
  `required_args` value matches only when it is equal
  (`crates/gglib-core/src/domain/benchmark/tune/task.rs`), so in the suite
  whose descriptions name a folder an absolute path under it scores as a
  miss, though the tools take it as is; the suites settle how a task scores
  that before they run. The entry that
  records it names the model, the build, the seeds and both runs' ids from
  `gglib benchmark list`.
- **Kill criterion 2's first reading** is due when the template's removal
  merges, and again 30 days later. Kill criterion 1's and 5's window opens
  when this line merges; their first reading is due 30 days after.
- **`stderr_tail.rs` does not link ADR 0023.** It is made by another
  change, not on this line; its `//!` gains the link in the next change
  that touches it.

## 2026-10-23: decision 4 holds under the server list

[ADR 0024](0024-the-tunnel-opens-mcp-servers-by-name.md) lets a paired
device's runs use the tools of the MCP servers `--allow-mcp` names. Decision
4 holds: a device's run is still composed with no folder, so gglib's own file
tools are never offered to it, and the list cannot name `builtin`, which is
refused when the tunnel is enabled. A filesystem MCP server the owner names
is an MCP server like any other; naming one is his decision.
