# ADR 0008 log

[ADR 0008](0008-two-binaries-one-daemon.md) log. Readings, measurements and
follow-up bookkeeping, appended and never edited; a line number refers to the
commit the entry names.

## 2026-09-26: both binaries inherit the workspace lints

Finding 1 describes the crates' lint tables as they stood when this ADR was
accepted. The change that made every workspace member inherit
`[workspace.lints]`, whose grandfathered allows #1157 tracks, replaced the
tables of `crates/gglib-cli` and `src-tauri` with `[lints] workspace = true`:

- `crates/gglib-cli/Cargo.toml` no longer re-declares `unsafe_code = "deny"`.
  The CLI inherits it from `[workspace.lints.rust]`.
- `src-tauri/Cargo.toml` no longer declares its own `[lints.rust]`, so
  `gglib-app` is under `unsafe_code = "deny"` as well. An `AttachConsole` call
  there would need an `allow(unsafe_code)` exemption, as `mod layer_shell;` in
  `src-tauri/src/tray/mod.rs` has.

The finding's statement that `gglib-app` "is not under the deny at all" no
longer holds. The `windows_subsystem = "windows"` attribute in
`src-tauri/src/main.rs`, on which the finding rests, is unchanged.

## 2026-10-07: the deletion criterion of finding 4 is met

Finding 4 records one exception to "both are clients of the daemon": the
desktop process checked for and installed llama.cpp itself, in
`src-tauri/src/commands/llama.rs`, and the frontend reached it through
`src/services/platform/llamaInstall.ts`. Its deletion criterion is that the
desktop install flow moves onto the HTTP route. The change this entry lands in
makes that move:

- The install prompt, `src/components/LlamaInstallModal.tsx`, which the app
  shell and the model inspector open, runs
  `POST /api/config/system/install-llama`, as the setup wizard does. A browser
  tab is offered the same install. Before, the app shell never opened the
  prompt in a browser, and from the inspector its button closed the prompt
  there without installing.
- The app shell reads whether llama.cpp is installed from
  `GET /api/config/system/setup-status`. The finding names
  `GET /api/config/system/llama-status` beside the install route; that route
  does not say whether a prebuilt binary can be downloaded, which the prompt
  needs, and setup-status does.
- `src-tauri/src/commands/llama.rs`, the `check_llama_status` and
  `install_llama` commands it held, the `llama-install-progress` event and
  `src/services/platform/llamaInstall.ts` are deleted.
  `scripts/check-frontend-ipc.sh` and `scripts/check-tauri-commands.sh` no
  longer allow them.

One direct call into `gglib_runtime::llama` is left in the desktop process, and
the finding did not name it: `sync_app_menu` in
`src-tauri/src/menu/state_sync.rs` calls `check_llama_installed` to enable or
disable the macOS menu's install item. It reads whether the binary is on disk
for a native menu, and installs nothing. The install and the prompt's status
check are no longer an exception to the claim in the finding's heading; the
menu's read is what is left of it.
