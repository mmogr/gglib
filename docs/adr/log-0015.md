## 2026-10-03: llama-server reads an image when it is started with the model's projector

A proof of concept of the engine side of image input. It is the evidence the
arc starts from: llama-server reads images once it is given the projector,
and what gglib lacks is that file's place in the library and on the launch
command line.

**Scope.** One machine, a 128 GB Mac on Metal. llama.cpp at `cb7934c`. One
model, Qwen3.8-27B at Q8_0, with a 629 MB mmproj GGUF as its projector. One
session, and no script for it is in the repository, so none of these numbers
can be re-derived from a checkout; the reproducer is the shape of the
session: llama-server started with `--mmproj <projector>`, and a chat
completion whose user message carries an `image_url` part. No other machine,
backend, model family or quantization was read.

**Readings.**

| Image | Prompt tokens | Prefill | Content read back |
|---|---|---|---|
| Terminal screenshot, 980x460 | 480 | 2.7 s | exactly |
| Screenshot, 2560x1440 | 3,646 | 24 s | exactly |

- **What the server reports.** With the projector, `GET /props` answers
  `modalities` as `{vision: true, video: true, audio: false}`. Without it,
  all three are `false`.
- **Without the projector an image request fails, and not by name.** It is
  HTTP 500 with the message "image input is not supported".
- **`--image-max-tokens 8192` changed nothing.**
- **A projector is not tied to the repository its model came from.** A
  projector from mradermacher's abliterated repository worked with unsloth's
  GGUF of the same base model.
- **Generation speed** was unchanged, at about 15 tokens per second.
- **Memory.** Resident set size was 29.2 GB.
