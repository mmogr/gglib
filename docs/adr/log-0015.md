# ADR 0015 log

The log of ADR 0015, image input, which is not written yet: the arc is open,
and the ADR is written from this log when the arc closes. Readings,
measurements and interim decisions, appended and never edited; a line number
refers to the commit the entry names.

## 2026-10-03: llama-server reads an image when it is started with the model's projector

A proof of concept of the engine side of image input. It is the evidence the
arc starts from: llama-server reads images once it is given the projector,
and what gglib lacks is that file's place in the library and on the launch
command line.

**Scope.** One machine, a 128 GB Mac on Metal. llama.cpp at `cb7934c`. One
model, Qwen3.8-27B at Q8_0, with a 629 MB mmproj GGUF as its projector. One
session, and no script for it is in the repository, so none of these numbers
can be re-derived from a checkout; the reproducer is the shape of the
session: llama-server started with `--mmproj <projector>`, and a chat
completion whose user message carries an `image_url` part. No other machine,
backend, model family or quantization was read.

**Readings.**

| Image | Prompt tokens | Prefill | Content read back |
|---|---|---|---|
| Terminal screenshot, 980x460 | 480 | 2.7 s | exactly |
| Screenshot, 2560x1440 | 3,646 | 24 s | exactly |

- **What the server reports.** With the projector, `GET /props` answers
  `modalities` as `{vision: true, video: true, audio: false}`. Without it,
  all three are `false`.
- **Without the projector an image request fails, and not by name.** It is
  HTTP 500 with the message "image input is not supported".
- **`--image-max-tokens 8192` changed nothing.**
- **A projector is not tied to the repository its model came from.** A
  projector from mradermacher's abliterated repository worked with unsloth's
  GGUF of the same base model.
- **Generation speed** was unchanged, at about 15 tokens per second.
- **Memory.** Resident set size was 29.2 GB.

## 2026-10-04: an image is counted by its pixels, and refused by name where it cannot be read

Interim decisions of the change that lets an outside client (Copilot, any
`OpenAI` client) send images through the proxy. The code is
`crates/gglib-core/src/request_pipeline/images.rs`, `image_size.rs` and
`measure.rs` at the commit this entry lands in.

**The estimate.** `estimate_image_tokens(w, h) = min(ceil(w/32) * ceil(h/32),
4096)`, at least 1. Against the two readings above:

| Image | Measured | Estimated |
|---|---|---|
| 980x460 | 480 | 465 |
| 2560x1440 | 3,646 | 3,600 |

Both estimates are under the measurement, by 15 and by 46 tokens: the prompt
tokens measured include the request's text and the chat template. Two images
of one model family on one machine are what the constants rest on; no other
family was read.

**The constants.** `IMAGE_TOKEN_PX = 32`, the side of the square one token
covers, from the 2560x1440 reading. `MAX_IMAGE_TOKENS = 4096`, the model
family's own cap on one image, and what an image is charged when its size
cannot be read: an `http(s)` URL, a format other than PNG or JPEG, or a header
cut short. The size is read from the header alone, and a base64 payload is
decoded only as far as the header runs, at most 1 MiB (`MAX_HEADER_BYTES`).

**The measurement.** History truncation measures a request at its serialized
length with each image at its estimated tokens times the chars-per-token
ratio in use, in place of the length of its URL. Without that, a 1.5 MB
screenshot was refused as `context_length_exceeded` under any context a local
model has.

**Calibration skips an image request.** The per-model chars-per-token ratio
is learned from a request's characters and the prompt tokens llama-server
reports. With an image aboard most of those tokens are the image's, so such a
request does not update the ratio.

**The session id covers the images.** The content-hash session id hashes the
URL of each image in the first user message after its text, so the same
words about two different screenshots are two sessions. A chat with no image
keeps the id it had.

**The refusal.** A request with an image anywhere in its messages for a model
with no projector is refused with HTTP 400 `model_cannot_read_images` before
admission. This change refuses at the proxy's chat completions; the agent
path, the hub and the CLI do not refuse yet.

**The body limit.** 32 MiB (`MAX_BODY_BYTES`) on the proxy's
`POST /v1/chat/completions` and `PUT /v1/runs/{id}`, with a coded 413
`request_too_large`. The daemon's `/api` routes are unchanged.

**Not measured.** The estimate against `usage.prompt_tokens` through the
proxy has not been read for this change; the table above compares it with
the proof of concept's readings, which were taken without the proxy.

## 2026-10-04: a projector is fetched with its model, and chosen by one rule

Interim decisions of the change that makes a downloaded vision model work
with no extra step. The code is `crates/gglib-core/src/download/projector_choice.rs`
and `crates/gglib-core/src/ports/huggingface/download_group.rs` at the commit
this entry lands in.

**The fault.** A repository listing grouped every `.gguf` by the quantization
in its name. So `mmproj-F16.gguf` was listed as an "F16" quantization of the
model, and `X.mmproj-Q8_0.gguf` joined the real `Q8_0` group as a second
shard. Files sort by name and the first is the primary one, so a projector
could become the file a model is launched from.

**The split.** A file's role is read once, from its name
(`GgufFileRole::classify`). A repository's quantizations are made of weights
alone, and its projectors are listed apart. A projector is never a
quantization and never a shard.

**The choice rule.** A download of quantization Q from a repository that has
projectors fetches one of them, picked by `choose_projector`:

1. the projector whose own name carries Q;
2. else the `F16` one;
3. else the first by name.

Where several satisfy an arm, the first by name is taken. The download, a
repair, `--list-quants` and the page's preview all ask this one function, so
a listing names the file the download fetches. There is no
flag to opt out at download; `gglib model update <model> --no-projector`
unlinks afterwards.

**The group.** The projector is one more file of the model's download group,
after the weights. The model's primary file is always a weights file. Shard
numbers, shard counts and the size shown as the model's count weights alone;
download progress covers every file. The projector keeps a `model_files` row,
so verification covers it.

**The link.** At completion the model is linked to the projector by the rule
`ModelService::set_projector` holds: the file's header must say it is a
projector. A file that fails the check leaves the model registered and
unlinked, and the completion message says why. A model the library already
holds with a link keeps that link when it is registered again.

**Update check and repair.** The update check of a model that has a projector
row compares it, by path, with the repository's projectors, so a changed
projector is seen as an update. A repair queues the model's group again, and
deletes an unhealthy projector only when that group fetches the same file,
so a corrupt projector is fetched again and one from elsewhere is left
alone.

**What a projector costs, as the preview says it.** Its file size in memory,
which is what launch already counts. And llama-server, at `cb7934c`, switches
off context shift and `--cache-reuse` when a projector is loaded
(`tools/server/server-context.cpp:1241-1249`), and makes no context
checkpoint after an image chunk (`:3819`). Reuse of a prompt's common prefix
is not gated on the projector (`:3376-3378`), so the plan's wording, "a model
with a projector does not reuse its prompt cache", is not what the source
says and was not used. This is a reading of the source; no cache behaviour
was measured.

**A reading.** `gglib model download unsloth/Qwen3.8-27B-GGUF --list-quants`
on 2026-10-04, at repository commit `4ca7207`, lists 25 quantizations, none
of them `F16`, and both projectors apart: `mmproj-BF16.gguf` (888.0 MiB),
fetched with `BF16`, and `mmproj-F16.gguf` (884.6 MiB), fetched with every
other quantization. The `BF16` quantization listed is the repository's
51 GiB weights in two shards. The listing is live, so it cannot be re-derived
once the repository changes; the file list it was read from is
`crates/gglib-hf/src/file_roles_fixture.json`.

**Not covered.** Three groups in that listing are still wrong, and none
involves a projector: `MTP/mtp-Qwen3.8-27B-Q4_0.gguf` is counted as a second
shard of `Q4_0`; `Qwen3.8-27B-UD-Q6_K_M.gguf` is counted as a second shard of
`UD-Q6_K`; and `imatrix_unsloth.gguf` is listed as a quantization named
`imatrix`. A projector cannot be downloaded on its own, and a projector
linked from another repository is not checked for updates.
