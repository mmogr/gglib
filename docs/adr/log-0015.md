# ADR 0015 log

The log of ADR 0015, image input, which is not written yet: the arc is open,
and the ADR is written from this log when the arc closes. Readings,
measurements and interim decisions, appended and never edited; a line number
refers to the commit the entry names.

## 2026-10-03: llama-server reads an image when it is started with the model's projector

A proof of concept of the engine side of image input. It is the evidence the
arc starts from: llama-server reads images once it is given the projector,
and what gglib lacks is that file's place in the library and on the launch
command line.

**Scope.** One machine, a 128 GB Mac on Metal. llama.cpp at `cb7934c`. One
model, Qwen3.8-27B at Q8_0, with a 629 MB mmproj GGUF as its projector. One
session, and no script for it is in the repository, so none of these numbers
can be re-derived from a checkout; the reproducer is the shape of the
session: llama-server started with `--mmproj <projector>`, and a chat
completion whose user message carries an `image_url` part. No other machine,
backend, model family or quantization was read.

**Readings.**

| Image | Prompt tokens | Prefill | Content read back |
|---|---|---|---|
| Terminal screenshot, 980x460 | 480 | 2.7 s | exactly |
| Screenshot, 2560x1440 | 3,646 | 24 s | exactly |

- **What the server reports.** With the projector, `GET /props` answers
  `modalities` as `{vision: true, video: true, audio: false}`. Without it,
  all three are `false`.
- **Without the projector an image request fails, and not by name.** It is
  HTTP 500 with the message "image input is not supported".
- **`--image-max-tokens 8192` changed nothing.**
- **A projector is not tied to the repository its model came from.** A
  projector from mradermacher's abliterated repository worked with unsloth's
  GGUF of the same base model.
- **Generation speed** was unchanged, at about 15 tokens per second.
- **Memory.** Resident set size was 29.2 GB.

## 2026-10-04: an image is counted by its pixels, and refused by name where it cannot be read

Interim decisions of the change that lets an outside client (Copilot, any
`OpenAI` client) send images through the proxy. The code is
`crates/gglib-core/src/request_pipeline/images.rs`, `image_size.rs` and
`measure.rs` at the commit this entry lands in.

**The estimate.** `estimate_image_tokens(w, h) = min(ceil(w/32) * ceil(h/32),
4096)`, at least 1. Against the two readings above:

| Image | Measured | Estimated |
|---|---|---|
| 980x460 | 480 | 465 |
| 2560x1440 | 3,646 | 3,600 |

Both estimates are under the measurement, by 15 and by 46 tokens: the prompt
tokens measured include the request's text and the chat template. Two images
of one model family on one machine are what the constants rest on; no other
family was read.

**The constants.** `IMAGE_TOKEN_PX = 32`, the side of the square one token
covers, from the 2560x1440 reading. `MAX_IMAGE_TOKENS = 4096`, the model
family's own cap on one image, and what an image is charged when its size
cannot be read: an `http(s)` URL, a format other than PNG or JPEG, or a header
cut short. The size is read from the header alone, and a base64 payload is
decoded only as far as the header runs, at most 1 MiB (`MAX_HEADER_BYTES`).

**The measurement.** History truncation measures a request at its serialized
length with each image at its estimated tokens times the chars-per-token
ratio in use, in place of the length of its URL. Without that, a 1.5 MB
screenshot was refused as `context_length_exceeded` under any context a local
model has.

**Calibration skips an image request.** The per-model chars-per-token ratio
is learned from a request's characters and the prompt tokens llama-server
reports. With an image aboard most of those tokens are the image's, so such a
request does not update the ratio.

**The session id covers the images.** The content-hash session id hashes the
URL of each image in the first user message after its text, so the same
words about two different screenshots are two sessions. A chat with no image
keeps the id it had.

**The refusal.** A request with an image anywhere in its messages for a model
with no projector is refused with HTTP 400 `model_cannot_read_images` before
admission. This change refuses at the proxy's chat completions; the agent
path, the hub and the CLI do not refuse yet.

**The body limit.** 32 MiB (`MAX_BODY_BYTES`) on the proxy's
`POST /v1/chat/completions` and `PUT /v1/runs/{id}`, with a coded 413
`request_too_large`. The daemon's `/api` routes are unchanged.

**Not measured.** The estimate against `usage.prompt_tokens` through the
proxy has not been read for this change; the table above compares it with
the proof of concept's readings, which were taken without the proxy.

## 2026-10-04: a projector is fetched with its model, and chosen by one rule

Interim decisions of the change that makes a downloaded vision model work
with no extra step. The code is `crates/gglib-core/src/download/projector_choice.rs`
and `crates/gglib-core/src/ports/huggingface/download_group.rs` at the commit
this entry lands in.

**The fault.** A repository listing grouped every `.gguf` by the quantization
in its name. So `mmproj-F16.gguf` was listed as an "F16" quantization of the
model, and `X.mmproj-Q8_0.gguf` joined the real `Q8_0` group as a second
shard. Files sort by name and the first is the primary one, so a projector
could become the file a model is launched from.

**The split.** A file's role is read once, from its name
(`GgufFileRole::classify`). A repository's quantizations are made of weights
alone, and its projectors are listed apart. A projector is never a
quantization and never a shard.

**The choice rule.** A download of quantization Q from a repository that has
projectors fetches one of them, picked by `choose_projector`:

1. the projector whose own name carries Q;
2. else the `F16` one;
3. else the first by name.

Where several satisfy an arm, the first by name is taken. The download, a
repair, `--list-quants` and the page's preview all ask this one function, so
a listing names the file the download fetches. There is no
flag to opt out at download; `gglib model update <model> --no-projector`
unlinks afterwards.

**The group.** The projector is one more file of the model's download group,
after the weights. The model's primary file is always a weights file. Shard
numbers, shard counts and the size shown as the model's count weights alone;
download progress covers every file. The projector keeps a `model_files` row,
so verification covers it.

**The link.** At completion the model is linked to the projector by the rule
`ModelService::set_projector` holds: the file's header must say it is a
projector. A file that fails the check leaves the model registered and
unlinked, and the completion message says why. A model the library already
holds with a link keeps that link when it is registered again.

**Update check and repair.** The update check of a model that has a projector
row compares it, by path, with the repository's projectors, so a changed
projector is seen as an update. A repair queues the model's group again, and
deletes an unhealthy projector only when that group fetches the same file,
so a corrupt projector is fetched again and one from elsewhere is left
alone.

**What a projector costs, as the preview says it.** Its file size in memory,
which is what launch already counts. And llama-server, at `cb7934c`, switches
off context shift and `--cache-reuse` when a projector is loaded
(`tools/server/server-context.cpp:1241-1249`), and makes no context
checkpoint after an image chunk (`:3819`). Reuse of a prompt's common prefix
is not gated on the projector (`:3376-3378`), so the plan's wording, "a model
with a projector does not reuse its prompt cache", is not what the source
says and was not used. This is a reading of the source; no cache behaviour
was measured.

**A reading.** `gglib model download unsloth/Qwen3.8-27B-GGUF --list-quants`
on 2026-10-04, at repository commit `4ca7207`, lists 25 quantizations, none
of them `F16`, and both projectors apart: `mmproj-BF16.gguf` (888.0 MiB),
fetched with `BF16`, and `mmproj-F16.gguf` (884.6 MiB), fetched with every
other quantization. The `BF16` quantization listed is the repository's
51 GiB weights in two shards. The listing is live, so it cannot be re-derived
once the repository changes; the file list it was read from is
`crates/gglib-hf/src/file_roles_fixture.json`.

**Not covered.** Three groups in that listing are still wrong, and none
involves a projector: `MTP/mtp-Qwen3.8-27B-Q4_0.gguf` is counted as a second
shard of `Q4_0`; `Qwen3.8-27B-UD-Q6_K_M.gguf` is counted as a second shard of
`UD-Q6_K`; and `imatrix_unsloth.gguf` is listed as a quantization named
`imatrix`. A projector cannot be downloaded on its own, and a projector
linked from another repository is not checked for updates.

## 2026-10-04: gglib's own surfaces name an image by its id, and the bytes are stored once

Interim decisions of the change that lets a user message of gglib's own
surfaces carry images: the CLI now, and the hub's routes the chat page and a
paired device will use. An outside client's inline `image_url` parts through
the proxy are as the second entry left them. The code is
`crates/gglib-core/src/services/attachments.rs`,
`crates/gglib-db/src/setup_attachments.rs` and
`crates/gglib-runtime/src/ports_impl/llm_completion/images.rs` at the commit
this entry lands in.

**By reference, and why.** A user message carries `images`, a list of ids,
beside its text (`AgentMessage::User`, `NewMessage`, `HubTurn`,
`RemoteTurnBody`); a saved row answers each as id, type, width and height
(`AttachmentInfo`), never bytes. Three things made inline bytes the wrong
form for gglib's own messages:

- gglib measures a request by its length in more than one place, and a
  megabyte of base64 is not a megabyte of prompt;
- a chat's whole history is sent again every turn, so an inline image would
  be stored and carried once a turn;
- a chat opened on a paired device would pull every image through the tunnel
  to list its rows.

**Stored once, as sent.** An image is a row of `attachments`, keyed by the
lowercase hex SHA-256 of its bytes; `message_attachments` links a message to
its images in order and goes with the message by cascade. One core function
takes an image in (`AttachmentService::ingest`), for the daemon's route, the
proxy's and the CLI. It reads the type from the first bytes (PNG or JPEG;
never a name or a `Content-Type`) and the size from the image's own header,
and refuses a file whose size cannot be read. The server never rewrites the
bytes: no decode, no resize, no re-encode. So the id is the hash of the file
the client holds, and the same bytes sent twice are one row and the same
answer. Any downscaling is the client's, before upload; the CLI does none.

**The id becomes bytes at one place.** The completion adapter reads each id
a request names from the store and writes it as an `image_url` data URL just
before the request is sent. A user message with no image is the bare string
it was before. This holds for a paired machine's model too: this machine
resolves the ids and its request to the far proxy carries the parts, as an
outside client's would.

**The caps, and where each is enforced.**

| Cap | Value | Enforced | Refusal |
|---|---|---|---|
| One image (`MAX_IMAGE_BYTES`) | 8 MiB | The ingest function; and as the body limit of `POST /api/attachments`, `POST /v1/attachments` and `POST /api/remote/attachments`, so an oversized body is refused while it arrives | 413 `image_too_large` |
| The images of one request (`MAX_REQUEST_IMAGE_BYTES`) | 16 MiB of raw bytes, history included | The completion adapter, before anything is sent | The run ends with an error event that says so; no HTTP status carries the code |
| One request body (`MAX_BODY_BYTES`) | 32 MiB | The proxy's `POST /v1/chat/completions` and `PUT /v1/runs/{id}`, from the second entry | 413 `request_too_large` |

16 MiB of raw bytes is under 22 MiB as base64, which with a chat's text has
to fit under the 32 MiB body limit of a far proxy. An image named twice in a
request is read once and counted twice, as it is sent.

**The other refusals.** `unsupported_image` (400) for anything but a PNG or a
JPEG whose size can be read. `attachment_not_found` for an id the store
lacks: 400 on a turn that names it, with nothing saved, and 404 on a read by
id. It is not 404 on a turn because a paired device reads a 404 on the runs
route as a hub with no runs.

**The refusal by name is now at every site.** `model_cannot_read_images`,
by the one predicate of the second entry, before any model load: an agent
run on a local server, by the model that server serves; a device's turn on a
hub chat, once its model is known; and the CLI, before the agent loop is
composed. The whole history counts. A model of the paired machine is not
judged here: its own proxy answers. Its refusal reaches the user as that
proxy's sentence with the status in front of it, so the code is not a field
of what this machine answers.

**The CLI on `--port`.** A session on a server named by its port has no
catalogue row to judge, so `GET /props` of that server is read:
`modalities.vision` false is the same refusal, and a server that does not
answer or does not say is sent the image.

**What pruning charges.** `AgentMessage::char_count` charges each image
`MAX_IMAGE_TOKENS` at the chars-per-token constant pruning already uses, with
no lookup of its size. That is the cap, so a small image is overcharged.

**Unlinked images.** An image is uploaded before the message that names it
is saved, so an unlinked row is the normal state of a turn in flight. Rows no
message links to, last stored more than a day ago, are deleted when the
daemon starts and at no other time; an open of the database by the CLI
deletes nothing. The day is there because a daemon's start does not mean no
turn is in flight: `gglib q --image` stores the image in the CLI's process
and then starts the daemon when none is up, and the first cut of the sweep,
with no age in it, deleted that image before its request was built. Storing
the same bytes again moves the row's `created_at` to now. An image uploaded
for a turn never sent stays until the first daemon start a day later.

**A far refusal's code.** The completion adapter renders an upstream's
refusal as `<status> <type> (<code>): <message>`, the code in brackets when
the body has both, so a paired machine's `model_cannot_read_images` reaches
the user with its code and not only its sentence.

**The far relay types what it serves.** `GET /api/remote/attachments/{id}`
answers from this daemon's origin, so it passes on the far machine's
`Content-Type` only when that is `image/png` or `image/jpeg`, answers
`application/octet-stream` otherwise, and sets `nosniff`, as the two local
reads do.

**Privacy.** No image bytes and no base64 are in a log line, an error, a run
event or a panic message: an error names an id, or on the CLI the file's
path.

**Not built.** The chat page's composer, thumbnails and its own check of
whether a model reads images: the page still sends text alone. Images in a
chat export and in `gglib run start`. A route for an image's facts without
its bytes, which nothing uses.

**Not measured.** Nothing in this change was read against a running model:
no llama-server was started and no paired tunnel was used. The tests drive
fake servers.

## 2026-10-04: the chat page attaches images, and a run's images are checked before it starts

Interim decisions of the change that gives the chat page images: pasted,
dropped or picked in the composer, sent by id, and shown in the turn. The
code is `src/hooks/useGglibRuntime/imageAttachments.ts`, `imagePrep.ts`,
`turnImages.ts`, `src/components/ChatMessagesPanel/components/ComposerImages.tsx`
and `MessageImages.tsx`, `src/hooks/useFileDropGuard.ts`, and on the daemon
`AttachmentService::check_request`, at the commit this entry lands in.

**Refused before the run (#1257).** A run's messages are checked before a
run is made of them: every image id they name, history included, must be
stored, and together they must be no more than 16 MiB, each read by its
size alone (`length(data)`), never its bytes. An id not stored is `400
attachment_not_found` and an over-cap total `400 request_images_too_large`,
at a local run and a run on the paired machine's model before a slot is
taken, and at a device's turn on a hub chat before its model is loaded. The
completion adapter's check stays, as the backstop for anything that reaches
it another way. `request_images_too_large` is now a coded `400
invalid_request_error`, no longer only a run's last error.

**Uploaded when added, never when sent.** assistant-ui empties the composer
before a send's attachments settle, so an upload that failed in `send` would
lose the draft. The adapter's `add` shows the image at once, uploads it and
marks it ready; `send` only waits for an upload still going and turns the
attachment into the stored image's id. A failed upload is said at once as a
toast, since assistant-ui only logs a paste or a drop that throws; its image
stays marked, and a send that carries it sends nothing and hands the draft
back.

**Handed back whole.** A send refused by code (`model_cannot_read_images`,
`attachment_not_found`, `request_images_too_large`, `image_too_large`,
`request_too_large`) puts its text and its images back in the composer with
a sentence by the code. Each upload is remembered by the `File` it was made
from, per store, so images handed back, or carried over a model switch (the
draft is now text and images), are not uploaded again; after
`attachment_not_found` they are forgotten, so adding them back uploads them
again. A send that carries an image uploaded for the other machine's store
(the chat list moved there with it in the composer) sends nothing, not even
the composer's own id for it, and says so; the message comes back, its
images added to this chat's store. One this chat's store already holds, the
list having gone there and come back, is sent as it is.

**Downscaled in the page.** An image is read as the store reads it (a PNG's
or a JPEG's header); one within 2560 px and 8 MiB goes as it is, one over is
redrawn on a canvas, a PNG kept as PNG when it fits and JPEG otherwise. The
picker offers PNG and JPEG only, and anything else pasted or dropped is
refused by name before it is shown.

**Images ride with the text.** Every user message of the history names its
images again, as the whole history is sent each turn. A regenerate keeps the
turn's images, an edit sends the edit composer's, and a reopened chat's rows
come back with theirs (id, type and size, no bytes). An image-only first turn
is titled "Image chat", since the title model is sent the text alone.

**One rule for the offer.** `canSee` decides whether the attach button, the
composer's paste and drop, and a paste into an edit are offered, every
composer of the thread reading the one answer: this machine's model by its
catalogue entry, the paired machine's by the row that machine lists for it,
a model not known yet offered. The paired machine's rows are read only for a
chat on one of its models, never for a local or a far chat. A far chat
always offers them: its model is chosen on the far machine, whose proxy
refuses by name. The cost shown is the upload's `image_tokens`, and its
share of the served context (the model's served default, else its own; the
paired machine's `context_window`); a far chat's is tokens alone.

**Shown with the credential.** A turn's image is read from its chat's store
(this machine's, or the far machine's for a far chat) with the page's bearer,
which an `<img>` cannot send, and shown as a `blob:` URL revoked when it
goes; a click enlarges it in the page's dialog. The desktop's main window has
Tauri's own drag and drop turned off, which otherwise takes every drop
before the page sees it. So the page refuses a file dropped anywhere but the
composer, or on it while the model cannot read images: it cannot open in
place of the page and lose the draft.

**A paired model is sent bytes.** A chat of this machine's on the paired
machine's model names this machine's ids, which the far machine does not
hold. This machine's completion adapter reads them and sends data URLs with
the far machine's key, as for a local model.

**Known limit.** assistant-ui sends an edit only when its text changed, so
an edit that adds or removes only an image does nothing.

**Not measured.** Paste, drop and pick were driven in jsdom with the page's
own events, and the downscaler was replaced by a fake there; nothing ran in
a browser or the desktop window, and no image reached a model. Whether that
window opens a dropped file the page has not refused was not tried.
