![LOC](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/mmogr/gglib/badges/gglib-ffi-loc.json)

The one Swift-facing surface of gglib, shipped as `GglibFFI.xcframework`: a
dynamic framework for iOS, the iOS simulator and macOS.

An app on a phone gets gglib's own behaviour from gglib's own code through
this crate, rather than from a Swift copy of it. Chat never crosses it: the
app talks to a gglib it serves over loopback HTTP, as it talks to one on a Mac.

## Architecture

This crate is a **surface** in the Adapter Layer, beside `gglib-cli`,
`gglib-axum` and `gglib-tauri`, and the only one an app links rather than runs.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                     iPhone or Mac app (Swift, ggchat)                       │
│      GGLib: gglib_ffi.swift, generated by uniffi and vendored by the app    │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ import GglibFFI
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                GglibFFI.framework (dynamic, one per slice)                  │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │                           ►► gglib-ffi ◄◄                             │  │
│  │    uniffi scaffolding · build_info() · the runtime async calls enter  │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                                 gglib-core                                  │
│                        domain::engine_pins (llama pin)                      │
└─────────────────────────────────────────────────────────────────────────────┘
```

A dynamic framework rather than a static library, so its Rust standard
library and allocator stay inside it and cannot collide with modelpipe-ffi's,
which an app links statically beside it.

`GglibFFI` is one name four ways: the framework, its binary, the
`framework module` its `Modules/module.modulemap` declares, and the C module
the generated Swift imports (`uniffi.toml`'s `ffi_module_name`). The Swift
module an app compiles the binding into is the app's to name; ggchat names it
`GGLib`.

The crate is a phone crate (`PHONE_CRATES` in the Makefile), so its closure
for `aarch64-apple-ios` reaches nothing desktop-only, and
`scripts/check_boundaries.sh` refuses a direct dependency on a CLI, GUI,
server, database or host-probe crate. CONTRIBUTING's "Crate Boundaries" has
the list.

## Internal Structure

```text
crates/gglib-ffi/
├── Cargo.toml          cdylib (the framework's binary) + lib (for the tests)
├── uniffi.toml         ffi_module_name = "GglibFFI"
├── build.rs            README for rustdoc; uniffi's version from Cargo.lock;
│                       the install name inside the framework (Apple targets)
├── src/
│   ├── lib.rs          setup_scaffolding!, the surface, the runtime decision
│   ├── build_info.rs   BuildInfo and build_info()
│   ├── runtime.rs      one 2-worker tokio runtime; in_runtime for async exports
│   ├── runtime_tests.rs
│   └── bin/
│       └── uniffi-bindgen.rs   the generator (feature `bindgen`), not shipped
└── swift/              generated, committed, held by `make ffi-binding-check`
    ├── gglib_ffi.swift
    ├── GglibFFI.h
    └── module.modulemap
```

- [`src/lib.rs`](src/lib.rs) calls `uniffi::setup_scaffolding!()` and says
  why the library owns a tokio runtime rather than taking uniffi's.
- [`src/build_info.rs`](src/build_info.rs) is the one export: the gglib
  version, the uniffi version and the llama.cpp pin a build was made from.
- [`src/runtime.rs`](src/runtime.rs) is the runtime every async export
  enters; its tests poll the adapter the way uniffi's Swift polls an export,
  on a thread with no tokio context.
- [`src/bin/`](src/bin/) holds the binding generator, built from this
  crate's own `uniffi` so the Swift cannot disagree with the scaffolding.
- `swift/` is what `scripts/apple/generate-swift.sh` writes. Edit the Rust,
  then run `make ffi-binding`; never edit these files.

## Building the framework

The crate builds and tests as plain Rust on every OS. The framework and the
Swift smoke test need macOS with Xcode:

| Command | Does |
|---|---|
| `make ffi-binding` | Regenerates `swift/` from the library |
| `make ffi-binding-check` | Fails when the committed `swift/` is not what the library generates |
| `make ffi-xcframework-fast` | Builds `target/apple/GglibFFI.xcframework` unoptimised, with the binding beside it in `target/apple/swift/`, and checks each slice (`scripts/apple/check-slices.sh`) |
| `make ffi-xcframework` | The same, optimised: what a release ships |
| `make ffi-smoke` | Compiles the binding in a scratch Swift package against the macOS slice and calls `build_info()` (`scripts/apple/swift-smoke.sh`) |

Both builds set `IPHONEOS_DEPLOYMENT_TARGET` and `MACOSX_DEPLOYMENT_TARGET`
to 26.0, ggchat's floor; `scripts/apple/build-xcframework.sh` says why they
must be set at all. CI's `ffi-apple` job runs the fast build, the binding
check and the smoke test whenever a change reaches the crate's inputs.
