# gglib-ffi

![LOC](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/mmogr/gglib/badges/gglib-ffi-loc.json)

The one Swift-facing surface of gglib, shipped as `GglibFFI.xcframework`: a
dynamic framework for iOS, the iOS simulator and macOS, which links llama.cpp's
own `llama.framework`.

An app on a phone gets gglib's own behaviour from gglib's own code through
this crate, rather than from a Swift copy of it. Chat never crosses it: the
app talks to a gglib it serves over loopback HTTP, as it talks to one on a Mac.

## Architecture

This crate is a **surface** in the Adapter Layer, beside `gglib-cli`,
`gglib-axum` and `gglib-tauri`, and the only one an app links rather than runs.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                     iPhone or Mac app (Swift, ggchat)                       │
│      GGLib: gglib_ffi.swift, generated by uniffi and vendored by the app    │
│      its OpenAI-compatible client, talking HTTP to the served base_url      │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ import GglibFFI
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                GglibFFI.framework (dynamic, one per slice)                  │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │                           ►► gglib-ffi ◄◄                             │  │
│  │   build_info() · open_library() → Library · DownloadWatch · runtime   │  │
│  │   Library.serve() → Server · EngineWatch                              │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└──────────────────┬───────────────────────────────────────┬──────────────────┘
                   ▼                                       ▼
┌─────────────────────────────────────┐  ┌────────────────────────────────────┐
│ gglib-bootstrap: the database, the  │  │ gglib-proxy on a port of loopback, │
│ Hub client, the download manager    │  │ admitting through InProcessRuntime │
└──────────────────┬──────────────────┘  │ gglib-engine-llama: shim, llama.h  │
                   │                     └─────────────────┬──────────────────┘
                   ▼                                       ▼
┌─────────────────────────────────────┐  ┌────────────────────────────────────┐
│ gglib-core: device_budget,          │  │ llama.framework (dynamic),         │
│ phone_fit, PHONE_SHORTLIST, ports,  │  │ llama.cpp at the pin               │
│ the catalog, engine_pins            │  │                                    │
└─────────────────────────────────────┘  └────────────────────────────────────┘
```

A dynamic framework rather than a static library, so its Rust standard
library and allocator stay inside it and cannot collide with modelpipe-ffi's,
which an app links statically beside it.

`GglibFFI` is one name four ways: the framework, its binary, the
`framework module` its `Modules/module.modulemap` declares, and the C module
the generated Swift imports (`uniffi.toml`'s `ffi_module_name`). The Swift
module an app compiles the binding into is the app's to name; ggchat names it
`GGLib`.

The crate is a phone crate (`PHONE_CRATES` in the Makefile), so its closure
for `aarch64-apple-ios` reaches nothing desktop-only, and
`scripts/check_boundaries.sh` refuses a direct dependency on a CLI, GUI,
server, database or host-probe crate. CONTRIBUTING's "Crate Boundaries" has
the list. The server it starts is gglib-proxy's, and the engine behind it
gglib-engine-llama's: both phone crates.

## The model library

`open_library(dirs, hf_token)` builds gglib's own core through
`gglib-bootstrap`'s composition root, over folders the app names: the
database (`gglib.db`) in `data_dir`, and every download in `models_dir`, a
folder per repository. The Hub is asked with `hf_token`, or else with the
`HF_TOKEN` the process started with, which an app on a phone has none of.

- **Verdicts.** The app samples its memory as a `DeviceReading` and gglib
  makes the budget from it (`domain::device_budget`). A verdict is
  `domain::phone_fit::fit_verdict` over a model's shape and weights at that
  budget: `Fits`, `Tight`, `TooBig`, or `Unknown` naming the input it lacks,
  with a `FitWhy` holding the numbers. `suggested` judges the rows of
  `PHONE_SHORTLIST` with no network. `quantizations` reads the first 64 KiB
  of each quantization's first file from the Hub and parses the head
  (`GgufParserPort::parse_head`); a key the head ends before is `cut_off`,
  since the file may still hold it. `installed` judges each model's row. The
  library holds the last reading handed to it, so the list of installed
  models is judged at the reading of the browse that showed it.
- **Downloads.** `download` asks the Hub for the quantization's files, so a
  refusal arrives as the Hub's own error, then queues it on the core's
  download manager, which resumes a `.part` with a ranged request, checks the
  file against the Hub's digest, and adds the model to the library. The
  manager reports to `DownloadFeed`, the core's event emitter, and each
  `DownloadWatch` reads where its download stands from there. Swift cannot
  cancel a call into Rust, so a watch is pulled with `next()` and stopped
  with `cancel()`. The manager has no pause: `pause_all` cancels what is
  queued, which keeps each `.part`, and waits for each to stop, and
  `resume_all` queues it again.
- **Removal.** `remove` deletes a model's files (every shard, and a projector
  or companion no other model names), then its row, then each folder it
  emptied.
- **Errors.** One `GglibError`: the Hub's 401/403, 404 and 429 are
  `AuthRequired`, `NotFound` and `RateLimited`, a full disk is `NoSpace`, and
  anything else is `Network` or `Internal` in gglib's words. A download that
  fails while it runs ends `Failed` with the download manager's words.

## The served engine

`Library.serve(reading)` starts gglib's own proxy (`gglib_proxy::serve`) on a
free port of 127.0.0.1, in front of gglib-engine-llama's `InProcessRuntime`,
and answers a `Server`: `base_url()` (`http://127.0.0.1:<port>/v1`),
`api_key()`, `status()` and `shutdown()`. The app's unchanged
OpenAI-compatible client talks to `base_url`; nothing of a chat crosses the
binding.

- **Composition.** As the agentic eval's in-process proxy arm composes one,
  for a phone: the runtime over the decoder this build has, the catalog over
  the library's models (`CatalogPortImpl`), an MCP service over its table of
  servers, which a phone leaves empty, and its settings. No prompt cache, no
  slot folder, no host facts (`HostFacts::none()`), no dashboard publisher,
  and `device_memory_readable`, since the budget is the engine's.
- **The key.** Every request must carry the serve's bearer: 32 bytes from the
  OS's random source, as hex, new for each serve (`ApiKeySource::Flag`). Every
  app on a phone shares its loopback. The engine's own port behind the proxy
  is told only to the proxy.
- **The budget.** `budget_from` the reading, made once and held for the
  serve, so every model admitted is fitted to the same number; the library
  holds the reading for its verdicts too. A reading with a zero in it is
  refused with `Internal` before anything listens or an engine served before
  is stopped, rather than by every request after. A model that does not fit
  is the proxy's 507, `model_does_not_fit`.
- **The decoder.** llama.cpp's, through
  `gglib_engine_llama::linked_llama_decoder(None)` (the decoder's own GPU
  default), where this build linked `llama.framework`: the crate's `llama`
  feature on an Apple target, which every slice of the framework is built
  with. Anywhere else `serve` answers `EngineUnavailable`. The surface is the
  same in both, so the binding is one. On the iOS simulator's slice `serve`
  runs llama.cpp on the CPU, fitted to the host's memory the reading reports;
  whether to offer it there is the app's call, and ggchat's engine factory
  answers `UnavailableEngine` on a simulator.
- **The watch.** `status()` is an `EngineWatch`, pulled with `next()`, which
  answers where the engine stands now, then each change, and `None` once it
  has answered `Stopped`. The runtime publishes seven states and the watch
  shows five (`EngineState`): `Idle`, `Loading{model, fraction}`,
  `Ready{model, n_ctx}`, `Failed{model, reason}` and `Stopped`. A reply being
  generated is `Ready` still, at the same `n_ctx`, the `context_size` its
  usage reports; a model being freed is `Idle`, since it is no longer served
  from the moment it starts to go. Two states that show the same are one
  answer.
- **Stopping.** `shutdown()` stops the proxy taking connections, ends the
  reply in flight, frees the model, closes the engine's port, ends every watch
  on `Stopped`, and waits up to five seconds for the proxy's last connections.
  It is idempotent. A `Server` the app lets go of without a shutdown is
  stopped on the library's threads. Serving again stops the engine served
  before and waits for its model to be freed, the one a `Server` let go of
  is still freeing too, so the device never holds two models.

## Internal Structure

```text
crates/gglib-ffi/
├── Cargo.toml          cdylib (the framework's binary) + lib (for the tests)
├── uniffi.toml         ffi_module_name = "GglibFFI"
├── build.rs            README for rustdoc; uniffi's version from Cargo.lock;
│                       the install name inside the framework (Apple targets)
├── src/
│   ├── lib.rs              setup_scaffolding!, the surface, the runtime decision
│   ├── build_info.rs       BuildInfo and build_info()
│   ├── runtime.rs          one 2-worker tokio runtime; in_runtime for async exports
│   ├── library.rs          LibraryDirs, open_library, Library and its calls
│   ├── reading.rs          DeviceReading, and the budget gglib makes of it
│   ├── verdict.rs          FitVerdict, MissingInput, FitWhy; a model's shape judged
│   ├── browse.rs           Suggestion, SearchHit/SearchPage, QuantOffer
│   ├── installed.rs        InstalledModel; removing a model's files and row
│   ├── downloads.rs        starting a download; pause_all and resume_all
│   ├── download_feed.rs    the download manager's emitter, kept per download
│   ├── download_watch.rs   DownloadWatch, DownloadProgress, DownloadState
│   ├── serve.rs            Server: the proxy in front of the in-process engine
│   ├── engine_watch.rs     EngineState, the runtime's seven shown as five; EngineWatch
│   ├── errors.rs           GglibError, mapped from the Hub's and the manager's
│   ├── *_tests.rs          each module's tests
│   ├── test_library.rs     the library a test is built over (test only)
│   ├── test_hub.rs         a Hub over gglib-hf's recordings (test only)
│   ├── test_server.rs      a fake of the Hub's file addresses (test only)
│   ├── test_gguf.rs        GGUF headers written in a test (test only)
│   └── bin/
│       ├── uniffi-bindgen.rs   the generator (feature `bindgen`), not shipped
│       └── add-model.rs        a GGUF on disk added to a library, for the
│                               Swift smoke test (feature `smoke`), not shipped
└── swift/              generated, committed, held by `make ffi-binding-check`
    ├── gglib_ffi.swift
    ├── GglibFFI.h
    └── module.modulemap
```

- [`src/lib.rs`](src/lib.rs) calls `uniffi::setup_scaffolding!()`, shows the
  surface's shape and says why the library owns a tokio runtime rather than
  taking uniffi's.
- [`src/build_info.rs`](src/build_info.rs) is the gglib version, the uniffi
  version and the llama.cpp pin a build was made from.
- [`src/runtime.rs`](src/runtime.rs) is the runtime every async export
  enters; its tests poll the adapter the way uniffi's Swift polls an export,
  on a thread with no tokio context.
- [`src/library.rs`](src/library.rs) is the library and every call on it;
  the modules after it in the tree each hold one concept those calls use.
  [`src/serve.rs`](src/serve.rs) composes the served engine and is the
  `Server`; [`src/engine_watch.rs`](src/engine_watch.rs) maps the runtime's
  states to the app's.
- The tests drive the exports from a thread with no tokio context, over a
  library built by `CoreBootstrap::build_with_hub` with a stand-in Hub:
  verdicts per quantization from gglib-hf's recorded model info and a written
  head, a 401, and downloads from a fake file server into a temporary models
  folder (progress, a cancel, a resume from the `.part`, a pause and a resume,
  a digest that does not match, the model joining the library, its removal). A
  served engine decodes with gglib-engine-llama's `ScriptedDecoder`, on any
  OS: served and shut down twice, the watch from `Idle` to `Stopped` and
  `None`, a 401 without the key, a streamed reply through the proxy whose
  `usage.context_size` is the `n_ctx` the watch shows `Ready`, a reading with
  a zero refused and the engine served before left serving, serving again over
  a server held and over one let go of mid-load, a server let go of, and
  `EngineUnavailable` where nothing is linked. The process's gglib data root
  is a temporary one (`paths::isolate_data_root`), so no test finds the user's
  own folder. They run without the `llama` feature: with it, on a Mac with
  `GGLIB_LLAMA_XCFRAMEWORK` set, a test binary links `llama.framework` with no
  run path to it and does not start, since only the engine crate's own tests
  are given one. The smoke test is where this crate meets the real decoder.
- [`src/bin/`](src/bin/) holds the binding generator, built from this
  crate's own `uniffi` so the Swift cannot disagree with the scaffolding, and
  the smoke test's helper.
- `swift/` is what `scripts/apple/generate-swift.sh` writes. Edit the Rust,
  then run `make ffi-binding`; never edit these files.

## Building the framework

The crate builds and tests as plain Rust on every OS. The framework and the
Swift smoke test need macOS with Xcode, and llama.cpp's `llama.xcframework` at
the pin, which every slice links: `make phone-llama` builds it in
`target/apple/llama-<pin>/`, or `GGLIB_LLAMA_XCFRAMEWORK` names another. The
smoke test also needs `GGLIB_ENGINE_MODELS_DIR` holding `tinygemma3-Q8_0.gguf`
(`.github/actions/pinned-engines/models.txt`).

| Command | Does |
|---|---|
| `make ffi-binding` | Regenerates `swift/` from the library |
| `make ffi-binding-check` | Fails when the committed `swift/` is not what the library generates |
| `make ffi-xcframework-fast` | Builds `target/apple/GglibFFI.xcframework` unoptimised with the `llama` feature, with the binding beside it in `target/apple/swift/`, and checks each slice (`scripts/apple/check-slices.sh`), its link to `llama.framework` included |
| `make ffi-xcframework` | The same, optimised: what a release ships |
| `make ffi-smoke` | Compiles the binding in a scratch Swift package against the macOS slice, with `llama.framework` beside it, calls every export that needs no network, then serves tinygemma3 and streams one reply from it through `URLSession` (`scripts/apple/swift-smoke.sh`) |

Both builds set `IPHONEOS_DEPLOYMENT_TARGET` and `MACOSX_DEPLOYMENT_TARGET`
to 26.0, ggchat's floor; `scripts/apple/build-xcframework.sh` says why they
must be set at all. CI's `ffi-apple` job runs the fast build, the binding
check and the smoke test whenever a change reaches the crate's inputs, with
llama.xcframework from the `llama-xcframework` action.

## Release assets

Each gglib release attaches the framework and its binding, built by
`release.yml`'s `build-phone` job with the runner's default Xcode:

| Asset | Holds |
|---|---|
| `GglibFFI-<version>.xcframework.zip` | `GglibFFI.xcframework`, optimised, at the archive's root, where Swift Package Manager looks for a binary target's framework |
| `GglibFFI-swift-<version>.zip` | `gglib_ffi.swift`, `GglibFFI.h` and `module.modulemap` as the build generated them, and `binding.json`, at its root |
| `llama-<version>.xcframework.zip` | `llama.xcframework`, llama.cpp's own at the pin `binding.json` names, which every `GglibFFI` slice links, at the archive's root |

`binding.json` names what `build_info()` reports, under the same field names:
`gglib_version`, `uniffi_version` and `llama_pin`. All three archives are in
the release's `SHA256SUMS` and carry build provenance. Each framework
archive's line there is what `swift package compute-checksum` reports, so an
app's `.binaryTarget(name: "GglibFFI", url:checksum:)` and
`.binaryTarget(name: "llama", url:checksum:)` take them as they stand; the app
embeds both.

`scripts/apple/package-release.sh` makes the three from a build and checks
them as an app meets them: the `GglibFFI` archive holds `GglibFFI.xcframework`
alone and unzips to slices `check-slices.sh` passes, the llama archive holds
`llama.xcframework` alone and unzips to slices `check-llama-xcframework.sh`
passes, a scratch Swift package takes both archives as binary targets and
gets back from `build_info()` what `binding.json` says, and the checksum
Swift Package Manager computes for each is its SHA-256.
