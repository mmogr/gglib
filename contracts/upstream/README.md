# contracts/upstream
What the pinned llama-server and sd-server answered, written by `make record-upstream` (`crates/gglib-runtime/src/engine_contract_tests.rs`).
Only `llama/approvals.json` is edited by hand; `make adr-readings` holds `llama/observed.json` to it.
`llama/bodies/` is copied in from a recording when a pin moves; its `apply-template.<template>.<thinking|no-thinking>.txt` are, verbatim, the prompts the pin renders for one fixed chat on each dateless template. `llama/tier3/` holds what Qwen3.5-0.8B did at the last llama.cpp bump, which no check reads. CONTRIBUTING's "The engine pins" says what a bump needs.

`llama-inproc/` is what the phone's engine answered the same questions with, on the same models: gglib-engine-llama's shim over llama.cpp's own `llama.xcframework` at the pin, in the test process, written by `make record-upstream-inproc` on a Mac (`crates/gglib-runtime/src/engine_contract_inproc.rs`). It is not asked what it refuses or does not serve (tools, a projector, `--help`), and its `/slots` is read as the 501 it answers. Its readings are all plain. Its `version.txt` is not a binary's `--version`: the `build_info` line is gglib's pin constant as the shim's `/props` serves it, and the `llama.xcframework` line is the `pin.txt` beside the framework the recording ran on, which is what names the llama.cpp that answered. Its `bodies/` are written with it, not copied in at a bump: `stream.sse`, a whole redacted stream ending in its usage, which a phone's stream readers take as their fixture; `stream-content.sse`, tinygemma3's greedy reply as a whole redacted stream, whose deltas carry `content`; and the six renders. Neither stream has `usage.context_size`, which gglib-proxy adds. `crates/gglib-runtime/src/engine_contract_parity.rs` holds it to `llama/` on every OS: each `shape.txt` line one `llama/shape.txt` has, the lines gglib reads present, `version.txt` at the pin, the renders byte for byte, and `greedy.tinygemma3.*` the same: the visible pieces tinygemma3 streams at temperature 0 (the one generated text either recording keeps), the prompt's and the reply's tokens, and its `finish_reason`. A token with no bytes streams no piece, so only the count holds it. `template_parity.<template>` and `greedy_parity.tinygemma3` say whether that held against the `llama/` beside it when it was recorded.
